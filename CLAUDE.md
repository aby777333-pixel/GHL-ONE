# GHL ONE — Company Operating System for GHL India Ventures

Next.js 16 (App Router, `src/`), React 19, Tailwind v4, Supabase (project `rarlrohsybktcheyrhiv`).
Positioning: *One Company. One Workspace. One Source of Truth.*

## Conventions (read before writing code)
- **Auth/session**: server pages call `getSession()` from `@/lib/session` (redirects to /login or /pending). Client components use `useSession()` from `@/components/providers/SessionProvider` → `{ profile, departments, people }`.
- **Supabase**: server → `createClient()` from `@/lib/supabase/server`; client → `createClient()` from `@/lib/supabase/client`. Types in `@/lib/database.types` (generated). Row/enum aliases + label maps + helpers in `@/lib/utils` (`Task`, `Project`, `STATUS_LABEL`, `PRIORITY_TONE`, `fmtDate`, `relDate`, `ago`, `isManagerPlus`…).
- **UI primitives**: `@/components/ui` — `Button`, `Pill`, `Avatar`, `AvatarStack`, `Card`, `CardHeader`, `Input`, `Textarea`, `Select`, `Field`, `SearchInput`, `Modal` (`side` for drawer), `Tabs`, `EmptyState`, `Spinner`, `Skeleton`, `Kbd`, `Stat`, `Progress`, `Menu`/`MenuItem`, `PageHeader`, `useToast()`.
- **Pickers**: `@/components/pickers` — `PersonPicker`, `DepartmentPicker`, `PriorityPicker`, `StatusPicker`, `ClassificationPicker`, `ProjectPicker`.
- **Task bits**: `@/components/tasks/TaskBits` — `StatusPill`, `PriorityPill`, `WaitingPill`, `DueLabel`, `PersonChip`, `TaskRow`. `@/components/tasks/QuickTaskForm` creates tasks.
- **Styling**: CSS tokens in `globals.css` (`var(--bg-elev)`, `var(--line)`, `var(--fg-muted)`, tones `.tone-*`, `.card`, `.btn`, `.input`, `.pill`, `.page`, `.h1/.h2/.h3`, `.eyebrow`, `.text-muted`). Golden-ratio spacing `--s1..--s7`. Dark mode = `.dark` on `<html>`; use tokens, never hard-coded greys. Mobile first: no horizontal overflow; bottom nav is 56px on <lg.
- **Routes** live under `src/app/(app)/…` (inside the shell). Auth pages outside: `/login`, `/pending`, `/auth/*`. Proxy at `src/proxy.ts` protects everything else.
- **Data rules** are enforced in Postgres (RLS + triggers). Notifications, task history, audit logs, calendar entries and project channels are created by triggers — do not duplicate in the client. RPCs: `search_all`, `company_pulse`, `department_health`, `workload`, `open_dm`, `mark_channel_read`, `my_unread_counts`, `task_from_message`, `create_project_from_template`, `create_delegation`, `related_to`.
- Roles: super_admin > director > executive > department_head > manager > team_lead > employee > intern > consultant > vendor > guest. Helpers `isAdminRole`, `isManagerPlus`, `isLeadPlus`, `isInternal`.
- Never run `next build` while `next dev` is running. Verify in the browser, then commit → push → deploy.

## Intelligence (Phase 2)
- Server-only AI layer in `src/lib/ai/` (`client.ts` = Anthropic SDK wrapper `complete()` / `extract()` + usage logging; `context.ts` = permission-safe context builders that ALWAYS use the caller's RLS-scoped Supabase client; `prompts.ts` = stable cacheable system prompts; `route.ts` = `withAI()` auth/error wrapper + summary cache helpers). Routes under `src/app/api/ai/*` (ask, brief, project-summary, meeting-extract, extract-tasks, delegate-parse, catch-up, risks, search, status). Client code uses `callAI()` and types from `@/lib/ai/types` and must handle `.disabled` (no `ANTHROPIC_API_KEY`).
- Model: `claude-opus-5` (override with `AI_MODEL`). Cheap routes use `effort: "low"`. The AI never executes actions — it proposes; humans confirm in the UI.
- Cached outputs live in `ai_summaries`; usage in `ai_usage` (admin-visible).

## Automation (Phase 3)
- Engine lives in Postgres (`0006_automation.sql`): `automations` (WHEN trigger_type + trigger_config → IF conditions → THEN actions; see `run_automation_action` for action JSON) fired by AFTER triggers via `fire_automations()` with a depth guard (max 2); `automation_runs` log; `schedule` triggers and the escalation ladder (`escalation_rules`) run on pg_cron (`run_scheduled_automations` every 5 min, `run_escalations` every 15 min, digests daily/weekly 08:30 IST). Recurring tasks: `tasks.recurrence` → next occurrence spawned on completion. Handoffs: `handoffs` table + trigger moves/assigns the task. Outgoing webhooks/Slack via `pg_net`; incoming via `/api/hooks/{token}` → `ingest_webhook()`; personal ICS feed via `/api/calendar/{token}.ics` → `calendar_feed()`.
- Template variables for automation text: `{{title}} {{assignee_name}} {{owner_name}} {{project_name}} {{department_name}} {{due}} {{link}} {{status}} {{priority}} {{actor_name}}`.

## Migrations
`supabase/migrations/*.sql` are the source of truth and are applied to the remote project via the Supabase MCP (`apply_migration`). Keep them additive.

## Multi-company platform (0022_platform.sql)
- **Hierarchy**: *platform* → *company (tenant)* → *department* → *team* → *person*. A tenant **is** an `organizations` row; `organizations` now carries `tenant_code`, `status` (trial|onboarding|active|suspended|read_only|archived|closed|pending), `plan`, `industry`, `country`, `timezone`, `email_domain`/`restrict_to_domain`, `custom_domain`/`domain_verified`, `logo_url`/`accent_color`/`welcome_message`, `terminology`, `limits`, `onboarding_stage`, `mfa_required`, `retention_days`.
- **Identity**: one person, many `memberships` (user_id + org_id + role + status). `active_workspace` holds the tenant they are currently in and `current_org()` resolves to it *only* when they have an active membership there or platform authority — otherwise to their profile's org. Switching is `set_active_workspace(p_org, p_reason)`; the picker list is `my_workspaces()`. **Never mix tenants in one view**: after switching, `router.refresh()` so every server component re-reads.
- **Platform roles** (`platform_admins.role`, `platform_role()`): `platform_super_admin` (owner — the only one who may edit `platform_admins`/`platform_assignments`/`platform_features`), `platform_ops` (create companies, change status), `platform_security`, `platform_support` / `platform_billing` / `platform_developer` (reach only the tenants listed in `platform_assignments`). `platform_can_touch(org)` is the gate; `platform_admin_invites` recognises a platform person by email before their first login. Platform staff are **not** members of any tenant.
- **Break-glass** (`start_break_glass` / `end_break_glass`): platform staff see administrative metadata by default; reading a tenant's *content* needs an open session with a written reason (≥12 chars), a justification category, a scope (`configuration`|`content`|`full`) and an expiry (5–480 min). Opening one notifies the company's own admins, writes `platform_audit_logs` + `security_events`, and shows a persistent banner in the shell until it is closed. The company's own door is `grant_support_access` / `revoke_support_access` (`/admin?tab=support`).
- **Company lifecycle**: `create_company(...)` (owner/ops only) → departments, channels, features, onboarding checklist, admin invite and a private onboarding room; `set_company_status(org, status, reason)` refuses `active` while `company_go_live_blockers(org)` is non-empty; `company_setup_health(org)` drives every progress bar. **Deletion is never offered** — only Suspend / Read-only / Archive, each with a typed reason.
- **Features**: catalogue in `platform_features`, per-tenant overrides in `org_features`. Read with `org_feature_enabled(key, org)`; write **only** through `set_org_feature(org, key, enabled, limit)` (audited).
- **RULE — every new table must carry `org_id` and an org-scoped policy** (`using (org_id = current_org() and …)`). A table that reaches its tenant only through a parent must be listed deliberately; `tenant_isolation_report()` flags anything missing and `tenant_isolation_probe(other_org)` (SECURITY INVOKER, runs under the caller's RLS) proves a second company reads zero rows. Both are the release check, surfaced at `/platform` → Isolation and on each company's Security tab.
- **UI**: `/platform` (command center), `/platform/[id]` (one company: Overview · Admins · Departments · Usage · Features · Security · Onboarding · Audit · Configuration), `/platform/new` (nine-step onboarding wizard). Components in `src/components/platform/*` (types + label maps in `lib.ts`). Every platform page re-checks `is_platform_admin()` server-side and `notFound()`s — hiding a nav item is never the control. `<WorkspaceSwitcher/>` in `AppShell` is the mandatory always-visible tenant indicator and turns orange (“Administrative mode”) when the viewer is in a company as platform staff.

## Web push + PWA (schema 0025_push.sql)
- **Why**: an in-app notification reaches nobody who is not already looking at a tab. Push is a *second* delivery channel — the `notifications` row stays the source of truth and every push failure is silent.
- **Flow**: any `insert into notifications` → AFTER INSERT trigger `notification_push_fanout()` → `net.http_post` to `push_config.hook_url || '/' || hook_secret` (same pg_net pattern as the webhook action in `0006_automation.sql`) → `POST /api/hooks/push/[token]` → `sendPushToUser()` → the browser's `/sw.js`.
- **Authentication — no service-role key.** Postgres calls the hook with no session, so the route authenticates with `PUSH_HOOK_SECRET` (constant-time compare, header or path) and every privileged read happens *inside Postgres*, in SECURITY DEFINER functions that re-check that same secret against `push_config.hook_secret`: `push_notification(secret, id)` (the row, as JSON), `push_targets(secret, user, org, kind)` (`{ok, quiet, subs}` — applies `in_quiet_hours()`, skipped for `kind in ('critical','action_required')`, and the org scoping, limit 25), `push_settle(secret, dead, shaky, delivered)` (prune / strike-out at 10 / stamp). Each returns a benign empty value on a wrong secret and never reveals whether a user or row exists, so `execute` is granted to `anon, authenticated` — the secret *is* the credential. The app itself runs on the anon key only; **do not reintroduce `SUPABASE_SERVICE_ROLE_KEY`** to "simplify" this.
- **Schema**: `push_subscriptions` (user_id, `org_id` + `push_subscription_org_default()` trigger mirroring `notification_org_default()`, unique endpoint, p256dh, auth, user_agent, last_used_at, failure_count; RLS = own rows for all operations + org-scoped SELECT for `is_admin()`/`security.manage`); `push_config` (one locked row: `hook_url`, `hook_secret`, `enabled` — **RLS on with no policies**, so a member can never select the secret). Writes go through `save_push_subscription()` / `remove_push_subscription()` (SECURITY DEFINER — a shared browser can hold another person's row on the same endpoint).
- **Tenant scoping**: a device belongs to the workspace it was registered in. `PushRegistrar` (mounted in `AppShell`) silently re-posts the subscription on every load so `org_id` follows a workspace switch, and the fan-out only targets subscriptions matching the notification's `org_id`. Company B never rings a device currently signed into company A.
- **Client**: `src/lib/push/client.ts` (`usePush()` → `{ ready, supported, permission, subscribed, blocked, subscribe, unsubscribe, message }`). **Permission is never requested on load** — only from a click. `blockReason()` distinguishes unsupported / iOS-without-install / denied / no-VAPID-key, each with a plain-language message in `BLOCK_MESSAGE`.
- **UI**: `PushOptInPrompt` (one dismissible line in `NotificationsPanel`, 30-day snooze in localStorage) and `PushOptIn` (the real toggle, in the profile's Notifications card next to `NotificationSettings`). Both in `src/components/notifications/PushOptIn.tsx`.
- **Service worker**: `public/sw.js` — push-only, no offline cache. A ring notification (`entity_type = 'live_room'` with `?invite=` in the link) gets `requireInteraction` plus **Accept** → `/live/<room>?invite=…&accept=1` and **Decline** → `POST /api/push/decline` (→ `respond_live_invite`). `pushsubscriptionchange` re-subscribes and re-posts. `sw.js` is excluded from the `proxy.ts` matcher; `/api/hooks/push/…` is already covered by the `/api/hooks/` anon allowlist.
- **Env**: `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `PUSH_HOOK_SECRET`. Missing any of them degrades to "push not configured" / "no-secret" — nothing throws. **`SUPABASE_SERVICE_ROLE_KEY` is NOT required — nothing under `src/` reads it and the running app never holds one** (the only consumer is `scripts/verify.mjs`, the out-of-band DB self-test in `docs/TESTING.md`). A service key bypasses every RLS policy in the product, which is the opposite of what tenant isolation is for.
- **PWA**: `public/manifest.json` (standalone, shortcuts, PNG + maskable icons in `public/icon-192.png`, `icon-512.png`, `icon-maskable-512.png`, `badge-96.png`). iOS delivers push only to an installed PWA — the opt-in says so instead of failing silently.

## Access control — Platform Owner, roles and permissions (schema 0035–0036)
- **The rule**: no permission = no access, and *admin is a role, not an amount of power*. `has_perm(perm, user)` is the single source of truth; `src/lib/permissions.ts` (`can`, `canAny`, `requirePermission`) and `usePermission`/`usePermissions`/`<Can>` both go through it. UI helpers hide controls — they are **never** the control. Every protected route, RPC and query is still checked in Postgres.
- **Precedence** (`has_perm`, highest first): platform owner reserved authority → active membership → **explicit individual DENY** → explicit individual ALLOW → employment status (probation/notice/suspended) → system roles → department default → level default → company super admin *bounded by `company_admin_limits`* → deny. The old first line was `if role = 'super_admin' then return true`, which made an explicit deny unwritable; individual rules are now evaluated first. Verified behaviour-identical against the previous logic across every user × permission (731 combinations, 0 mismatches) before anything was built on it.
- **Platform owner** = `platform_admins.role = 'platform_super_admin'`. `is_platform_owner()` / `is_platform_owner_user(uuid)`. Holds platform authority outright — the one unconditional branch, so the owner cannot lock themselves out. Keys prefixed `platform.` never resolve inside a company for anybody.
- **`permissions`** is the catalogue (key, label, description, `grp`, `risk` standard|elevated|high, `requires[]`, `platform_only`). Add a new key here or it will not appear in the studio, in `effective_permissions`, or in any risk/dependency warning.
- **`company_admin_limits`** caps what one company's own administrators may hold and hand out (`admin_ceiling(org)`; null = unrestricted, which is every existing company). Only the platform owner writes it; a company may read its own ceiling.
- **Nobody grants what they do not hold**: `can_manage_permission()` + BEFORE triggers on `permission_overrides`, `system_roles` and `role_defaults`. You must administer permissions, hold the key yourself, stay inside the ceiling, and have `security.manage` for high-risk keys; you cannot grant yourself anything. `guard_platform_admins` stops a tenant touching platform staff and stops the last owner deleting or demoting themselves. All authority changes land in `permission_changes` (before/after/actor).
- **Reads**: `explain_permission(user, perm)` returns the whole precedence chain (the "why can/why not" answer); `effective_permissions(user)`; `preview_user_access(user)` / `preview_role_access(role)` are **simulations, never impersonation**; `permission_holders(perm)` answers "who can see this?"; `role_change_impact(role, perms)` gives the diff, high-risk callout, dangling dependencies and affected-people count *before* a save; `access_review_board()` lists high-risk holders, temporary grants, acting roles and authority left on people who have gone. `system_role_versions` snapshots every role change and `restore_system_role()` rolls one back.
- **Guards must fail closed.** `can_review_access` first returned NULL for an unauthenticated caller (`p_user = auth.uid()` is NULL), and `if not NULL then raise` never fires — the guard fell open. Coalesce every guard to false. Equally: revoking an RPC from `anon` does nothing on its own, because the privilege comes from the PUBLIC grant a new function receives by default — `revoke … from public` **and** `from anon`, then grant `authenticated` back.
- **UI**: `/platform/access` (`src/components/access/*`) — Roles (action matrix + diff + impact + version history), People (effective access, per-key allow/deny/expiry, "Why?"), Permissions (catalogue + "who has this"), Company limits (owner only), Access review. Re-checked server-side and again inside every RPC.

## RBAC — granular permissions and the Company Super Admin (schema 0040–0042)
- **Module × action catalogue (0040)**: the catalogue was broad verbs (`view`, `create`, `edit`, `delete`) plus a few `<module>.manage` keys, which cannot express "may edit the wiki but not delete people". It is now `module.action` — `people.view`, `files.upload`, `announcements.publish`, `roles.assign` — 125 keys, of which 76 are granular. **Every granular key records the broad key it refines in `permissions.legacy_alias`, and `has_perm` resolves the key OR its alias.** A role written against `view` therefore still satisfies `people.view`, `wiki.view` and `files.view`: the split grants nothing new and takes nothing away. Verified behaviour-identical across every user × every pre-existing key (833 combinations, 0 mismatches) before anything was built on it. `permissions.module` / `.action` are informational; authorisation is always by key.
- **Precedence is unchanged**, and the exact key beats its alias: an explicit deny on `people.export` is not undone by an inherited allow on `export`. Employment-status restrictions (probation/intern lose download, share, export) follow the alias too, so `files.download` is blocked for the same people `download` always was.
- **Adding a key**: insert it into `permissions` with a `legacy_alias` pointing at the broad key that used to govern it, or null if it governs something genuinely new. The Access Studio's role matrix renders straight from the catalogue (`byGroup`), so a new key appears in the editor, in `effective_permissions`, and in the risk/dependency warnings with no front-end change.
- **`company_super_admin` (0041) is a security role, not a level.** "Runs this company" used to mean `profiles.role = 'super_admin'` — a hierarchy level, which is organisational identity. **Job title, hierarchy level and security role are three separate things and none of them may be derived from another**: `designation` is a job title and is display-only, `profiles.role` is where someone sits in the chain of command, and authority comes from `system_roles` held through `user_roles`. `is_company_super_admin()` is the check; it is bounded by `admin_ceiling()` exactly as the level branch is, and `platform.%` keys never resolve for it. Existing level-super-admins were backfilled once so nobody lost access; the two move independently from here. Never write `if role = 'super_admin'` (or anything reading `designation`) into an authorisation path — `test_access_control()` fails the build if `has_perm` ever mentions a job title.
- **Two guards that were missing (0041)**: `trg_guard_user_role` — nobody may *assign* a role granting a permission they do not hold themselves, nobody may give themselves a role, and a role containing a high-risk key needs `security.manage` to hand out. Deliberately narrower than `can_manage_permission()`, which asks "may you edit the catalogue" and would have blocked HR from making somebody an Employee. `trg_last_super_admin_profile` / `trg_last_super_admin_role` — a company can never be left with no administrator, counting both routes to the authority, refusing with the message the brief specifies.
- **Fixed in passing (0041)**: `log_permission_change()` read `new.perm` outside the branch that knows the column exists. plpgsql resolves a record field against the row's real composite type before the surrounding `CASE` picks a branch, so on `system_roles`, `role_defaults` and `company_admin_limits` it raised `record "new" has no field "perm"` — **creating a security role or saving a level default had been failing outright**. Read a record field only inside the branch whose table has it.
- **`access_control.view`** names the Access Control screen and refines `security.manage`, so a company can let somebody review who holds what without letting them change it. Both the nav item and the page gate accept either key; the page still re-checks server-side and every RPC re-checks in Postgres.

## Permission scope — own / team / department / company (schema 0043)
- **`has_perm` answers *may you*; scope answers *over whom*.** `permission_scopes` narrows a permission's reach; it never grants one and never denies one. With no rule configured the answer is `company`, which is what the system already did, so the table is inert until somebody deliberately narrows something.
- **Why it must only narrow**: authority in this codebase does not all come from `has_perm`. `profiles`' update policy grants on `is_manager_plus() OR is_hr()`, and managers/directors hold no `people.edit` at all. A scope check that answered "false — you hold no such permission" would have taken profile editing away from every manager on deploy. It answers `company` for them instead (no opinion) and the existing gate stands.
- **Resolution**, most specific first, mirroring `has_perm`: `user → role → department → level → default → company`. The first source with a rule decides; *within* one source the **widest** rule wins, because holding two roles should union their reach, not intersect it. `permission_scope(perm, user)` returns `{scope, department_ids, source}`; `in_scope_user(perm, target)` and `in_scope_department(perm, dept)` are the thin predicates to use in policies. `department_ids` empty = "their own department", non-empty = those named departments (the brief's SELECTED DEPARTMENTS).
- **Enforced today in exactly one place**, and deliberately so: `profiles`' `profile_admin_update` policy now also asks `in_scope_user('people.edit', id)`. That is RLS — typing an id into a request is checked by the same rule — and it closes a real over-grant where a Design manager could edit an IT employee's record. Verified 0 permission drift across 2,125 user × key combinations, and that a manager holding no `people.edit` still reaches everyone.
- **Wiring more surfaces**: add `and in_scope_user('<perm>', <owner column>)` (or `in_scope_department`) to that table's policy. Do not filter in a server query instead — a hidden row is not a control. Resource-level scope for tasks, projects, files, the wiki and chat is wired as of 0047/0049; `can_view_task` / `can_view_project` / `can_view_channel` and the `files_read` / `wiki_read` policies are the controls there.

## Audit records outlive the people in them (schema 0044)
- `audit_logs.actor_id` pointed at `profiles(id) ON DELETE SET NULL` while the table carries an append-only trigger. The two contradicted each other, so **deleting anyone who had ever done something auditable failed** with `audit_logs is append-only` — offboarding hid it by deactivating rather than deleting. The log now stores `actor_label` (filled by a BEFORE INSERT trigger, so no call site changed) and has **no foreign key to profiles**: who acted is a historical fact, not a live pointer. Append-only is untouched.
- Corollary for any new audit-shaped table: record the actor's name at write time and do not make the row depend on the account still existing.

## Role-level deny, and why "why?" can no longer lie (schema 0046)
- **`system_roles.denied_permissions`** takes a permission away from everyone holding the role. It mirrors the `screens` / `denied_screens` pair the same table already uses, so it is the schema's own idiom rather than a new mechanism. Deny beats allow, as everywhere else here: an explicit deny on any held role outranks an allow on **another** held role, the department default and the level default.
- **It sits below the company-super-admin branch on purpose.** If a role could bind the company's top administrator, handing them a restrictive role would be a way to neuter the only person who can undo it — and the last-Super-Admin guard would not catch it, because they would still *hold* the role while being unable to use it. To bind a company super admin, use an individual override or the platform owner's `company_admin_limits` ceiling. Both are deliberate, visible acts.
- **Aliases resolve correctly in both directions**: denying broad `delete` also denies `tasks.delete` (the overlap catches the alias), while denying `tasks.delete` leaves broad `delete` alone (the broad key's `keys` array does not contain the narrow one). Same `&&` operator as allows, so the two tiers cannot disagree about what a key covers.
- **The precedence chain, complete** (highest first): platform owner → active account → `platform.*` never resolves in a company → individual DENY/ALLOW (exact key, then alias) → employment status → company super admin *bounded by the ceiling* → **role DENY** → role allow → department default → level default → super-admin level *bounded by the ceiling* → deny.
- **`explain_permission` no longer computes its own verdict — it returns `has_perm`'s.** 0040 taught `has_perm` to resolve a granular key through its alias and 0041 gave it the company-super-admin branch; `explain_permission` learned neither, so it answered "nothing grants this" for all 76 granular keys while `has_perm` allowed them. Roughly 1,200 wrong "why" answers, on the screen administrators trust when deciding whether someone's access is correct. The chain now explains and `has_perm` decides, so they cannot disagree about the answer again — the worst a future change can do is leave the *wording* behind. `test_access_control()` asserts the verdict still comes from `has_perm`, and also flags any role that both grants and denies the same key (deny wins, so the grant is dead config).
- **UI**: the role matrix is tri-state — click cycles inherit → allow → deny. "Inherited" is not "no access", and the tooltip says so: the key can still arrive from a department, a level or another role. Saving writes both arrays; version history and `restore_system_role` carry the denies, so restoring a version cannot silently drop them.

## Resource scope for tasks and projects (schema 0047)
- **`task_in_scope(task)` / `project_in_scope(project)`** are consulted by `can_view_task` / `can_view_project`, which are the RLS controls *and* what `search_all` filters by — so a narrowed reviewer cannot reach a task by typing its id or by searching its title. Same contract as people scope: they only ever narrow, and with no rule configured `permission_scope` answers `company` and both return true. Verified by counting what all 16 active people could see before and after: 332 task views, 15 project views, unchanged, 0 people affected.
- **Levels**, mapped onto what the tables record (neither has `team_id`, so team resolves through the people involved): `own` = named on it in any capacity (assignee, owner, creator, delegator, approver, waiting-on, collaborator) or, for a project, owner/creator/member — the brief's "assigned projects"; `team` = own plus anything whose assignee or owner shares your team; `department` = own plus the row's own department (or the named departments), with a task's missing department falling back to its assignee's, so unfiled work cannot escape a department-scoped reviewer; `company` = everything.
- **"Own" is the floor for every narrower scope.** Work addressed to you personally never falls out of your reach because somebody narrowed your department, so `department` returns own ∪ department. When testing, this is why a department scope can legitimately return the same count as `own`.
- **Performance**: these run once per row inside RLS, so `permission_scope` short-circuits on one indexed probe (`permission_scopes_lookup_idx`) when the company has no rule for the key — the overwhelmingly common case — instead of walking all five precedence sources.
- **Scope is only real where a control consults it.** `scope_enforced_permissions()` is the list — today `people.edit`, `tasks.view`, `projects.view`, `files.view`, `wiki.view`, `chat.view` — and `test_access_control()` fails if a scope rule exists on any other key, because a rule that narrows nothing while looking like a control is worse than no rule. Extend that function whenever you wire a new surface, and a second check asserts `can_view_task` / `can_view_project` still call their predicates at all.
- **UI**: the "Reach" card under a role's permission matrix (`RoleReach` in `RoleMatrix.tsx`) sets own / team / department / everyone per enforced key, writing `permission_scopes` rows with `subject = 'role'`. "Everyone" is the *absence* of a rule, so choosing it deletes the row and returns the key to the system default. Keep `SCOPED_KEYS` in step with `scope_enforced_permissions()`.

## Scope for files, the wiki and chat (schema 0049)
- **`file_in_scope` / `wiki_in_scope` / `channel_in_scope`** complete the set. Files and the wiki are enforced in their **RLS policies** (`files_read`, `wiki_read`); chat is enforced inside **`can_view_channel`**, which every chat read already funnels through. Same contract throughout — narrows only, inert with no rule. Enforced keys are now `people.edit`, `tasks.view`, `projects.view`, `files.view`, `wiki.view`, `chat.view`.
- **`search_all` had to be changed too, and this is the general lesson.** It is SECURITY DEFINER, so RLS does not apply to it and each branch re-implements its own checks. Wiring the policies alone left global search able to surface a narrowed file's name and folder. **Whenever you narrow a table, check whether `search_all` reads it directly** — `test_access_control()` now asserts search keeps calling `file_in_scope` and `wiki_in_scope` so this specific leak cannot come back, but a new table needs its own assertion.
- **Membership is the floor for chat, above even "own".** A person in a channel keeps it whatever the rule says, and a DM is never scoped away from its participants. Files fall back department → project's department → owner's department; wiki falls back to its author's; nothing unfiled can escape a department-scoped reviewer.
- **Both new SELECT policies carry a direct owner branch** (`owner_id = auth.uid() or file_in_scope(id)`, `author_id = auth.uid() or wiki_in_scope(id)`) — not decoration. `test_returning_policies` caught `files_read` the moment the predicate went in: a STABLE helper reading the table it guards runs against a pre-write snapshot, so `.insert().select()` would read back nothing. The helper already returns true for the owner, but only the policy text is visible to the planner. See `docs/TESTING.md`.
- Verified 0 drift across every active person (5 files / 15 wiki / all channels unchanged), narrowing confirmed to bite (wiki 3→0→3, channels 12→11→12), and the search leak confirmed closed and then reopened by removing the rule. `platform_self_test()`: 19 passed, 0 failed.

## Tenant isolation for the authority tables (schema 0050)

- **`user_roles` and `permission_overrides` carried no `org_id`**, so neither could have a policy mentioning `current_org()`. Their predicates were row-independent — `is_admin() or is_hr() or has_admin_perm('security.manage')` says nothing about *which* row is being touched — so once a branch was true it was true for **every row in the table, in every company**.
- **Demonstrated before it was fixed**, against a company-B person created inside a rolled-back transaction: a company-A director read their role grant, read their individual override, and **deleted the override**. The override was a *deny*, so deleting it grants that person access in a company the actor has nothing to do with. Re-run after the fix: 0 rows read, 0 deleted, and the escalating insert refused with *“That person is not in this company.”*
- **The guards did not close it**, and the reason generalises: `guard_permission_override` did check the target's company but is `BEFORE INSERT OR UPDATE`, so **DELETE never reached it**; `guard_user_role` had no company check at all. A trigger that skips an operation is why the tenant boundary belongs in RLS, on a column — a policy cannot skip a command.
- **`has_perm` joined `user_roles` to `system_roles` with no company test**, so a role belonging to company A attached to a person in company B would have granted its permissions inside company B. Now `sr.org_id = p.org_id` in both the deny and the allow tier. Verified 0 such rows exist, so it changed no live answer — it removed the possibility. Verified 630 user × key combinations against the pre-0050 logic recomputed inline: **0 drift**.
- **The company on an authority row is derived, never supplied.** `authority_row_org_default()` reads it from the *subject's* profile and overrides whatever the caller passed, so nobody can file a grant under the wrong company. The column also has `default current_org()` — not for correctness but because `NOT NULL` with no default makes the generated TypeScript `Insert` type demand the column at five call sites that have no business knowing it.
- **Why the self test had been reporting this as fine.** `tenant:no_org_column:review` read `rep->'child_tables_no_org'` and coalesced a missing key to `[]`. `tenant_isolation_report()` never emits that key, so the line printed “every non-global table carries org_id” on every run while 65 tables did not. **Coalescing an absent key to empty turns “not measured” into “nothing to report”** — the report now computes the list itself. It correctly reports 61 tables today (most legitimately reach their tenant through a parent).
- **`authority_tables()` is the list that may not rely on a parent**: `user_roles`, `permission_overrides`, `permission_scopes`, `system_roles`, `role_defaults`, `permission_changes`, `system_role_versions`. `access:authority_tables_tenanted` fails if any of them lacks `org_id` or an org-scoped policy, and `access:no_cross_company_roles` fails if anybody holds a role from another company. The review line cannot catch this class because it is informational by design — authority needs a check that is allowed to fail.

## Safe admin delegation — the roles.* keys become real (§15, schema 0051)

- **Four keys had been gating nothing.** `roles.create`, `roles.edit`, `roles.delete` and `roles.assign` have been in the catalogue since 0040; role administration was actually reached through `is_admin()`, which is `role_rank(current_role_level()) <= 2`. Three directors could edit and assign security roles for no reason but their rank — the exact thing §3A committed against. **A key that appears in the matrix, can be granted and revoked, and changes nothing is worse than no key**, because somebody will grant it and believe they delegated something.
- **Seeded before enforced, because making a key real is a narrowing.** The seed is small: all four `roles.*` keys and both `access_control.*` keys already alias `security.manage`, so every security administrator resolved them anyway. Only the level route needed writing down — `director` and `executive` level defaults, which is exactly what `is_admin()` covered. `super_admin` needs nothing (has_perm has an unconditional branch); the two roles holding `people.manage`/`hr.manage` are both Company Super Admin, which holds `security.manage`.
- **`admin_roles` was deliberately NOT seeded.** “HR Admin” lists `people.manage`, and letting that keep implying role administration is the over-grant §15 exists to remove. It has no holders, so nobody is affected — but this is the one place the change is intentionally not behaviour-preserving, and that is the point of the section.
- **Split per command**, because §15 names them separately and one `FOR ALL` policy cannot tell “may create a role” from “may delete one”: `sr_insert`/`sr_update`/`sr_delete` and `ur_insert`/`ur_update`/`ur_delete`. `has_admin_perm` not `has_perm`, so the `admin_assignments` wildcard route keeps working. **The manager branch on `user_roles` is untouched** — a manager assigning a role no stronger than their own level to their own report is a real workflow §15 does not ask anyone to remove.
- **Verified end to end, with row counts not exceptions.** `UPDATE`/`DELETE` filtered out by RLS affect zero rows *silently*; only `INSERT … WITH CHECK` raises. A first probe that measured “no error” reported everything working when it was not measuring anything — **never test an RLS write by catching an exception.** With row counts: all five active people keep create/edit/delete/assign, and denying `roles.edit` on one director stops role editing (t→f) while create and assign stay intact.
- **New `delegation` suite**, asserting the reverse direction from the scope checks: every key that *names* a capability must be referenced by some policy (`delegation:keys_enforced`); no policy on the authority tables may grant on `is_admin()` (`delegation:authority_not_from_rank`); and create/edit/delete must be separately gated (`delegation:role_commands_separate`). The second check **failed on its first run** and found `po_read` still granting by rank — fixed to `access_control.view`.
- **UI**: `AccessCaps` is passed from the page into `AccessStudio` → `RolesTab` / `RoleMatrix` / `PersonAccess`. New, Duplicate, the tri-state cells, Review change and Change are each disabled with a tooltip naming the missing key, and a read-only viewer gets one line explaining that reading this screen and changing it are different permissions. **The flags are a courtesy, never the control** — every write still goes through RLS.

## Authority changes are announced (§20, schema 0052)

- **Nothing told anybody.** `user_roles` and `permission_overrides` carried guard, history and org triggers and notified no one — a person could be given, or quietly stripped of, a security role and never hear about it. The only table in this area that notified anything was `admin_assignments`, the legacy path, which has no holders at all.
- **Two audiences.** The **subject**, always — it is their access, and §33's principle is that everything an employee's data shows is visible to the employee too. The company's **other super admins**, for *sensitive* changes only. “Sensitive” is not a judgement call: it is whether the catalogue marks the key `risk = 'high'`. The actor is never notified of their own action and the subject is never told twice.
- **Events**: role assigned / removed / expiry changed (`notify_role_grant`), individual allow / deny / rule removed (`notify_override_change`), account deactivated or reactivated and Super Admin level gained or lost (`notify_account_change`). All `kind = 'security'`, so they fan out to web push through the existing `notification_push_fanout()` — inserting the row is the whole delivery mechanism.
- **Department change is deliberately NOT covered.** `apply_transfer` already notifies the subject, and a trigger cannot tell whether that RPC is driving the update, so a trigger here would double-notify the sanctioned path. **A department change made outside the transfer flow (bulk import, direct edit) still notifies nobody** — a known gap, recorded rather than papered over.
- **The profiles trigger carries a `WHEN` clause** (`old.is_active is distinct from new.is_active or old.role is distinct from new.role`), so ordinary profile edits never enter the function at all.
- `delegation:authority_changes_notify` asserts the three triggers are attached, because a detached notification trigger looks exactly like a system where nothing is happening.
- **Fixed in passing**: `KIND_ICON` in `NotificationsPanel.tsx` had no entry for `security` or `help_request`, both valid `notification_kind` values, so those notifications rendered with an empty icon slot. Every notification this migration adds is `security`.

## Feature entitlements gate modules (§25, schema 0053)

- **`USER ACCESS = COMPANY FEATURE ENABLED AND USER HAS PERMISSION`.** Both halves existed — `platform_features`, `org_features`, `set_org_feature()` and `org_feature_enabled()` are all implemented and administered at `/platform/[id]` → Features — but **nothing consulted them**. `org_feature_enabled` was referenced by no policy, no access function and nowhere in `src/`; turning a feature off changed nothing.
- **The fourth control that was only a label**, after the granular keys (0040), the scope rules (0043) and the `roles.*` keys (0051). Worth naming as a pattern: **a table that stores an intention is not a control until something asks it a question.** Each of the four now has a self-test check that fails if it stops being asked.
- **`screens.feature_key` is the mapping**, because a “module” in this codebase *is* a screen — `effective_nav` and `proxy.ts` both derive from `effective_screens`, so gating there removes the module from sidebar, router and everything downstream at once, which is what §5 demands. 15 screens are mapped; `NULL` means part of the product and never gated (Home, Inbox, Approvals, Search, Admin…).
- **It is an outermost AND, never a precedence tier.** The chain answers “may this person” and its most specific entry wins; entitlement answers “does this company have the thing at all”. Verified: with Projects switched off, an individual override granting `projects` to a named person still yields `allowed = false`.
- **Zero drift on deploy**, verified by fingerprinting all 195 person × screen answers before and after — identical. All 15 mapped features are `default_enabled = true` and no company had disabled any. The three features that default to off (`external_guests`, `federation`, `api`) are capabilities rather than modules and deliberately map to no screen; gating one would have taken something away on deploy.
- **`source` is the token `feature_disabled`, not prose.** The no-access screen must *handle* this case, not merely display it: for a permission rule it offers Request access and a company administrator can act; for an entitlement nobody inside the company can say yes, so the form would send a request to people with no way to fulfil it. The page hides the form, changes the wording and points at whoever manages the subscription. Match `FEATURE_DISABLED` from `@/lib/screens`, never the sentence.

## Every surface that offers a destination is governed (§5, §19)

- The sidebar and mobile nav were already filtered (`filterNav(navFor(…), screens)`). **The command palette and quick capture were not**: both carried hardcoded destination lists — `/projects/new`, `/delegate`, `/meetings`, `/approvals`, `/announcements`, `/chat`, `/calendar`, `/people` — offered to everyone. `proxy.ts` still refused the page on arrival, so this was never an access breach, but §5 is explicit that a module the viewer cannot reach must **disappear from the palette and the create menus**, not merely be blocked.
- **The rule is one line: an entry that leads somewhere carries a `path`, and is shown only if `canOpen(path)`.** `canOpen` reads `effective_screens`, so it already accounts for role rules, department defaults and — since 0053 — whether the module is in the company's plan. Anything new added to `CommandPalette.actions` or `QuickCapture` must carry its `path` or it silently escapes governance.
- **Search results are filtered too, and for a different reason.** `search_all` already refuses rows the caller may not see; this is the other half — a row you may read can still live behind a module switched off for you, and offering to navigate there is exactly the leak §19 warns about.
- **`isPathAllowed()` fails OPEN when it cannot match a screen**, so a typo'd path is silently allowed. Every path used as a gate was checked against the `screens` table; all twelve resolve. Re-check that when adding one.
- **Command Center stopped being gated on rank.** It was `isManagerPlus(profile.role)` — which §3A rules out, and which disagreed with the sidebar the moment a company wrote a screen rule for it. Now `canOpen('/command')`. Verified no drift: the screen's own default is `manager+`, exactly what the rank test encoded.
- **Quick capture's tabs are derived, never corrected in an effect.** If the selected kind is unavailable the first available one wins (`active`), and the save handler branches on `active` rather than the raw selection — branching on the selection would have shown “Your idea” while saving a note.

## Access Control → Audit Log (§18, schema 0054)

- **Everything §18 asks to track was already being written, and nothing read it.** `permission_changes` (what a role, a level or a person may do), `config_history` (roles assigned and revoked, roles created and deleted, screen rules), `role_history` (level, title, status, department) and `audit_logs` — none of them referenced anywhere in `src/`. `access_audit()` is the read side, and the **Audit log** tab in the Access Studio renders it.
- **Two defects had to be fixed first**, because a log that cannot say who acted, or that can be edited, is not an audit trail:
  - **The actor outlives the person now.** All three history tables had `actor_id`/`changed_by` as `REFERENCES profiles(id) ON DELETE SET NULL` — the same defect 0044 fixed on `audit_logs`, and **worse**, because those tables have no append-only trigger, so the delete succeeded and hollowed out the trail silently instead of failing loudly. They now stamp `actor_label` at write time and carry no FK.
  - **`role_history` was cross-tenant.** No `org_id`, and `rh_read`'s `is_hr()` branch is row-independent — an HR person in one company could read another company's promotions, demotions and the reasons given. Same fix as 0050; `role_history` joins `authority_tables()`.
- **The wording is composed in the database, not the component**, so the log reads the same rendered, exported, or queried directly during an incident.
- **`access_audit()` is SECURITY DEFINER with one explicit gate**, deliberately not INVOKER: the three source tables have three different audiences (`pc_read` wants audit.read/security.manage, `ch_read` also admits `is_admin()`, `rh_read` admits HR and a person's own manager), and running under those would give a ragged feed where a manager saw a promotion but not the permission change that came with it. Verified it refuses an ordinary employee by name.
- **`person_id` and `role_id` are separate from `target_id`.** The first draft filtered on the display target, which for a role assignment is the `user_roles` ROW id — so filtering by person returned nothing for exactly the events an administrator most wants to trace. **Display and filtering are different jobs.**
- **`history_actor_label()` walked into the 0041 trap while being written**: `case when tg_table_name = 'role_history' then new.changed_by else new.actor_id end` raises on the tables without that column, because plpgsql resolves a record field against the row's real composite type before the CASE picks a branch. It broke every authority write until the round-trip probe caught it. **Read a record field only inside the branch whose table has it.**
- `audit:actor_survives_deletion` and `audit:history_is_append_only` guard both defects. Append-only here is achieved by the tables having **no write policy at all**, so the second check fails if anyone adds an UPDATE, DELETE or ALL policy to them.
- **Not captured**: IP and device, which §18 lists as "if available". Nothing records them for these events today.

## Fourth test report — 11 issues (schema 0055 + UI)

- **`body { overflow-x: hidden }` broke `position: sticky` application-wide.** A non-visible `overflow-x` computes `overflow-y` to `auto`, so body became a scroll container; the topbar then stuck to *body's* scrollport while the page actually scrolls on `html`, so it slid away on every long page. The guard now lives on `main` — a sibling of the topbar, ancestor of no fixed chrome — as **`overflow-x: clip`**, which does the same job without creating a scroll container, so sticky sub-bars inside pages keep working too. **Never put `overflow` on `body` in this codebase.**
- **Creating a channel with members left it empty (0055).** `channels.visibility` defaults to `invite_only`; `cm_insert` asked `can_view_channel(channel_id) OR user_id = auth.uid()`, and at the moment members are written the creator is not a member *yet* — so the row for anybody else failed, and one failing row fails the whole statement, taking the creator's row with it. Hence “0 members · 1 online”. **It only ever worked for administrators**, via `can_view_channel`'s `communication.manage` branch — which is why testing as an admin never showed it. - **Profile was duplicated** in the topbar menu and the sidebar footer. One identity, one place: the sidebar block is gone and the topbar menu carries name, title, department, email and the person's own **employee code** — which also settles the recurring confusion with the company code beside it in the workspace switcher.

## Bulk administration (§29)
- `BulkActions` in `src/components/admin/people/BulkImport.tsx` (reached from **Admin → HR → Employee records → Bulk import**) does five things to a multi-selection: **give a role, take a role, change department, change manager, deactivate**. ## Go-live audit — runtime failures nothing was watching (schema 0057–0058)

- **`INSERT … SELECT DISTINCT` resolves untyped literals to text before the insert target can coerce them.** `select distinct u, 'approval', …` into `notifications.kind` raises; `VALUES` and a plain `SELECT` do not. It broke `attendance_daily_summary()` (every run since 2026-09-08), `messages_after()` (a Connect message needing approval could not be inserted at all) and `start_access_review()`. A bare `null` in the same position fails the same way (`null::uuid`). Cast every literal in a DISTINCT insert.
- **A BEFORE UPDATE guard also intercepts FK `ON DELETE SET NULL`.** Postgres performs the referential action as an ordinary UPDATE. `department_guard()` restored `head_id` for any non-admin caller, and a cascade has no session, so deleting a department head left a dangling `head_id` and `attendance_cron_tick()` failed 54 of 144 runs a day. Guards now stand down when `auth.uid() is null` (the convention `guard_user_role` already used) — check any other BEFORE UPDATE guard that restores a column with an FK action.
- **`test_runtime_health()`** (suite `runtime_health` in `platform_self_test()`) fails when an active cron job's most recent run failed, and when the DISTINCT-literal pattern reappears. The cron log had been the only witness. Note it reports the *last* run, so it stays red until each fixed job has run once.
- **Verify a data fix by reading the row back.** 0057's cleanup reported success and changed nothing — the guard reverted it. 0058 ends with an assertion that raises if a department still points at a missing head.

## Function oracles closed (schema 0059)

- **A definer function that returns one boolean is still a disclosure.** 0045 closed the anonymous path to functions that read or wrote content; the yes/no helpers were left because they "change nothing". Each still answered a question about somebody else: `platform_role(<id>)` named the platform owners to an anonymous caller, `workspaces_for_email` confirmed which company an address had an account in, and `live_running_late` had no check at all, so anyone holding a meeting id could notify its participants.
- **Removing `anon` from a policy helper is safe when** every policy using it is `TO authenticated` and every function calling it is SECURITY DEFINER. Check both (`pg_policies.roles`, `prosecdef` of callers) before revoking, then prove it: 0059 fingerprinted row counts on all 213 tables for anon, two platform owners and a director before and after — identical.
- **Platform-identity helpers answer only about the caller** (`platform_role`, `is_platform_admin_user`, `platform_can_touch`, `has_break_glass`) unless the caller is platform staff or there is no session. Every existing call passes `auth.uid()`. The membership helpers (`is_live_host`, `collab_can`, `is_internal_user`…) deliberately still answer cross-user for signed-in callers — `start_live_room` checks invitees with them.
- **`workspaces_for_email` before sign-in matches the company's `email_domain` only**; the per-account branch requires the signed-in caller to be asking about their own address.
- **Testing inside a rolled-back block**: rows written to a temp table inside the subtransaction you roll back are rolled back too. Carry results out in a variable (e.g. the message of the exception that performs the rollback).

## A sign-up reaches the people who can admit it (schema 0060)

- **Nothing told anybody.** `handle_new_user()` creates the profile inactive and notified no one, so "Account awaiting activation" was a dead end: three real sign-ups had been sitting unseen. There was also nowhere for the person to say which department they belong to, so even an administrator who found the row had no idea whose colleague this was. Both halves are the fix — `join_requests` (the person's own statement: department, designation, note; it grants nothing) and `account_approvers(org, department)` (who that statement should reach).
- **Activation had been impossible below director, silently.** `profile_admin_update` admits `is_manager_plus() OR is_hr()`, but `profile_guard()` reverts `is_active` for every caller who is not `is_admin()` (rank ≤ 2) — and reverts rather than raises, so a department head clicking **Activate** got a success toast and nothing happened. `approve_account()` is the sanctioned path: it checks the authority itself, then names the person in `ghl.account_approval` so the guard stands down **for that row only** — the `ghl.transfer_notified` idiom from 0056. The guard is otherwise untouched, so an ordinary self-update is still reverted (verified: a pending user updating their own row to `is_active = true, role = 'super_admin'` touches 1 row and changes nothing).
- **Who may admit, exactly** (`can_approve_account(user, department)`): Super Admin and the `company_super_admin` role, who bypass the hierarchy entirely — any person, any department; director and above, and HR, which is precisely who could activate before, so nothing was taken away; and the new delegation — the head of the department being joined (`departments.head_id`) and that department's own department-head-level people. `account_approvers()` is the same rule read the other way round, so a notification never goes to somebody who would then be refused. **Do not reach for `people.edit` here**: granular keys resolve through `legacy_alias`, so `people.edit` is satisfied by anyone holding broad `edit` — a content role would have become an approver.
- **Nobody admits somebody above their own level.** `role_rank(new) < role_rank(mine)` is refused unless the approver is a Super Admin. The modal offers the same slice of the hierarchy, as a courtesy — the database is the control.
- **One notice, not two.** `notify_account_change()` already announces an `is_active` flip; a first approval now reads "Your account has been approved" instead of "reactivated", keyed off the same flag, and its department-move notice stands down for the department the person was just admitted into. §20's behaviour for an ordinary reactivation or transfer is unchanged.
- **Both activation paths converge.** Admin → People → Activate still writes `profiles` directly; `profiles_close_join_request` resolves any open request on a false→true flip, so the request list cannot keep showing somebody who is already inside.
- **The sign-up notification fires only for a self sign-up** (`auth.uid() is null` inside the AFTER INSERT trigger — GoTrue has no session), so a bulk import does not notify five administrators per row, and the whole fan-out is wrapped in an exception block: a notification failure must never fail the registration itself.
- **Routes**: `/pending` now carries the request form (it is outside the app shell, so it has no `ToastProvider` — messages are inline; `dept_read` is org-scoped rather than member-scoped, which is why a pending account can list departments). Approvers work at **`/people/requests`**, which inherits the `people` screen rule by path prefix — no new `screens` row, so nothing could be denied by default. `pending_accounts()` returns only rows the caller may act on, `can_approve_accounts()` gates the page, and `AccountRequestsLink` renders nothing when there is nothing to answer.
- Verified end to end in a rolled-back transaction: a Sales head sees the Sales request and not the Design one, their approval actually activates the account with the right department and role, they are refused on another department's request and on handing out a level above their own, a Super Admin is unbound, and an ordinary member is refused. `platform_self_test()`: 33 passed, 0 failed.

## Buddy intelligence orchestrator — stage 1 (schema 0061)

- **"Auto · picks by your role" was doing exactly and only that.** `pickAssistant()` reads role, department and tenure; the *question* was never looked at. A developer in Sales asking about a 500 error got the Sales persona and chat-mode instructions, and someone typing "why is this stuck?" got no blocker trace unless they first found the right quick-action button. `src/lib/ai/orchestrator.ts` is the layer that reads the request — the words, the page, the attachments — and decides intent → mode, persona hint and effort. The option now reads **Auto · picks by your question**.
- **Three invariants make it additive.** (1) *A quick action is an instruction, not a hint*: when the composer sends a mode other than `chat`, the request behaves byte-identically to before — that mode, no persona hint, no intent note in the prompt, and the same effort floor; only the routing annotation is new. (2) *The persona hint is a suggestion to `pickAssistant`, not an override of it* — it travels as the existing `override` argument, which already checks `enabled` and the department allow-list, so routing can never hand somebody a persona they were not entitled to, and it never touches `action_level`. (3) *Rules first, model second*: the keyword+context pass is free and deterministic; only a genuinely ambiguous sentence (confidence < 0.45, ≥ 24 characters) costs a classifier call.
- **The classifier is Haiku 4.5 with a 6-second timeout whose failure mode is "use the rules result"** — wrapped in try/catch returning null, so a slow or broken router is invisible. `AI_ROUTER=off` disables it; `AI_ROUTER_MODEL` overrides the model. **Haiku 4.5 rejects `output_config.effort` with a 400** — only `format` goes in `output_config` on that call. It is imported dynamically inside `classifyWithModel` so the rules path pulls in no client at all, which is also what makes the router testable on its own.
- **Effort can only be raised, never lowered.** The per-mode floor (`medium` for debug/check/incident, else `low`) is unchanged; `maxEffort()` lifts it for intents that deserve more thinking — an incident runs at `high`, a blocker trace at `medium`.
- **Tested against real sentences, not assumed.** A harness drives `routeBuddy()` over 23 representative questions with the model path off. It found two genuine misroutes on the first run: `cannot read propert` can never match "properties" (the trailing word boundary sits before the "i"), and "Teach me React hooks" tied 3–3 with the coding rule and lost on insertion order. Both fixed; 23/23 now route as intended, including the negatives that must *not* be dragged anywhere clever ("hi", "thanks!", "What is the dress code?"). **When adding a rule, add its case to `scripts/router-cases.mjs` (`npm run test:router`, 25 cases, exits non-zero on a misroute)** — a keyword table is exactly the kind of code that looks right and is not. It runs with `--conditions=react-server` so `server-only` loads outside Next.js, and needs no API key.
- **`ai_messages.routing` records the decision** (intent, mode, assistant, source, confidence, signals). Diagnostic only — nothing reads it to decide anything, so a wrong value cannot widen access — but an answer that went wrong is almost always an answer that was *routed* wrong, and without the decision on the row a bad answer is indistinguishable from a good answer to the wrong question. The mode pill on the message shows " · auto" with the detected intent on hover when Buddy chose the mode itself.
- **Correction — the keys ARE set.** An earlier note here said `ANTHROPIC_API_KEY`, the LiveKit pair, `VAPID_PRIVATE_KEY` and `PUSH_HOOK_SECRET` were missing from Netlify. They are not: `netlify env:list` defaults to the **dev** context, and every one of them is set on **production** for both sites. `/api/ai/status` returns `{"enabled":true,"model":"claude-opus-5"}`. Check the context before concluding a key is absent.

## Buddy memory with provenance — stage 2 (schema 0062)

- **Memory could not say where it came from.** `ai_memory` was `(user_id, key, value, updated_at, org_id)`, the `remember` tool wrote `{text}`, and the route read `select key,value limit 12` with **no ordering** and rendered a flat bullet list. Two defects in one line: the twelve rows it happened to return had nothing to do with what the person was doing, and a note Buddy *inferred* in passing read exactly like something the person had *stated*. "Where did you get that?" was unanswerable.
- **The layers already existed; a fourth was not built.** Personal working context → `ai_memory` (own rows only). Department and company knowledge → `ai_knowledge`, already owned, reviewed, classified and gated by `can_view_classification`. Everything live → the RLS-scoped tools. **`aim_all` is untouched and personal memory stays personal**: `project_id` / `department_id` on a memory are *tags* saying when it is relevant, never a grant to anybody else — sharing personal memory is precisely where an AI memory layer leaks. The sanctioned path from personal note to company record already exists and is explicit: a `knowledge_article` proposal a human approves, which is what keeps AI-inferred notes and authoritative records distinguishable (§13).
- **`kind` is the distinction that matters**: `fact` (they stated it) · `preference` · `instruction` (a standing instruction) · `decision` · `inference` (Buddy worked it out) · `uncertain`. The prompt block labels every line with its kind, source and age, and marks inferences and anything below 0.5 confidence as *treat as unconfirmed*. An inference must never be able to read as a fact.
- **`ai_memory_history` makes `version` mean something.** A memory that silently changes its mind is what makes an assistant untrustworthy, so a BEFORE UPDATE trigger keeps the previous value and `remember_fact` returns what it used to say ("It used to say X — tell them you have updated it"). The history table has **no INSERT policy**: only the trigger writes it.
- **The RPCs are SECURITY INVOKER, deliberately.** `aim_all` already says "your own rows, in your own company", so RLS is the control and an unauthenticated caller reads nothing rather than being told it read nothing. `remember_fact` / `recall_memory` / `memory_provenance` / `forget_memory` / `my_memory`, all revoked from `public, anon` and granted to `authenticated` (0059's rule: the PUBLIC grant is where the anon privilege actually comes from).
- **New Buddy tools**: `recall` (search their own memory), `why_you_know_that` (source, dates, confidence and the full correction history), `forget_that`. `remember` keeps its exact name and behaviour and now records provenance automatically; the tool description tells the model to set `kind` honestly and never to save anything about another person.
- **Verified in a rolled-back transaction, as the users themselves** (`set local role authenticated` + a JWT claim, so RLS actually applies): version 1 → 2 on a correction with the previous value carried back, project-tagged memory ranked first, an expired memory excluded from recall, provenance reporting kind and source, `forget` removing both the row and its history, and **a second person seeing 0 rows of it**. `platform_self_test()`: 33 passed, 0 failed.
- **UI**: `MyBuddyMemory` in the Privacy Center — everything Buddy holds about you, where each piece came from, whether Buddy inferred it, and a Forget button on every row. §33 again: an assistant that builds a private picture of somebody they cannot read is exactly what that principle rules out.

## Buddy stages 3-5 — models, the learning loop, the console, verified actions (schema 0063-0064)

### Model-independent architecture (§16) — `src/lib/ai/models.ts`
- **There was nowhere to say "this workload, that model".** Every feature read one string, `AI_MODEL`; the only exceptions were `ai_assistants.model` (a per-persona override) and the router, which hard-coded Haiku *and* had to know inline that Haiku rejects `output_config.effort`. `pickModel(task, {override})` resolves, most specific first: caller override → per-class env (`AI_MODEL_CHAT`, `AI_MODEL_REASONING`, `AI_MODEL_EXTRACT`, `AI_MODEL_SUMMARY`, `AI_MODEL_BULK`, `AI_ROUTER_MODEL`) → `AI_MODEL` → class default.
- **Defaults are not a cost decision.** Every class still resolves to what it used before — Opus 5 — except `router`, Haiku since 0061. Moving a workload to a cheaper model changes answer quality, which is the company's call: it is one environment variable away, and the console now reports what each class costs so the call can be made on evidence. A class default outranks the global `AI_MODEL` (only `router` has one) so pointing the product at a larger model cannot silently slow every auto-routed question.
- **`outputConfig(model, effort)` is the capability gate.** Haiku 4.5 answers a request carrying `effort` with a **400**, not a worse answer — exactly the kind of thing that is discovered in production unless one place owns it. `complete()` and `extract()` now return the model they used.
- Prices live in `src/lib/ai/pricing.ts`, which is **client-safe on purpose** (the console does the arithmetic in the browser) and re-exported by `models.ts`. The database stores no prices. `estimateCostUsd` returns **null** for an unknown model — an unknown price is not zero, and the console says so rather than adding a made-up number to a total.

### The learning loop (§13) — 0063
- **Feedback had been collected since 0011 and read by nobody.** A knowledge article three people had marked wrong was handed to Buddy exactly as confidently as one nobody had ever questioned. `knowledge_signal(ids)` returns **counts only** — never the note, never who — and `search_knowledge` now appends *"N unresolved reports that this is wrong"* to the article as it retrieves it. That is the loop closing: the signal reaches the answer, not just a queue.
- `answer_quality(days)` groups by `ai_messages.routing ->> 'intent'` — **this is why 0061 records the routing decision on the row**. "Which questions does Buddy answer badly" is unanswerable without knowing what kind of question each answer was. It also reports the grounded rate (did the answer use live data or approved knowledge at all) and the insufficient rate, which is the honest measure of a knowledge gap rather than a model problem.
- `knowledge_health(days)` joins citations and flags per approved article via `ai_messages.context @> [{"kind":"knowledge","id":…}]`; `ai_cost_summary(days)` returns tokens by model and feature. All three are gated on `can_see_ai_console()` — **the same gate as the AI control centre they sit in**, so the console grants nobody anything new. A GIN index on `ai_messages.context` keeps the containment lookups off a sequential scan.

### Conflicting knowledge (§14)
- SQL cannot tell whether two documents disagree, so the division of labour is: **SQL finds the candidates, the model reads them, the answer reports the conflict.** `search_knowledge` says so when it returns more than one article; `compare_sources(ids)` returns 2-4 articles in full with owner, department, last-updated, review date and unresolved-report count, read through the caller's own client so `aik_read` decides what comes back. The system prompt forbids resolving a disagreement silently: say they disagree, give the deciding facts, and if that is not enough say the answer cannot safely be established. **A confident answer drawn from one of two conflicting sources is worse than no answer.**

### Completing the console (§15) — 0065
- **`assistant_performance(days)`** reports per *persona* — answers, grounded rate, insufficient rate, proposals, flags — from the assistant recorded on each answer by 0061. Per persona, **never per person**: the unit on this screen is the question, and "who asks Buddy the most" is not a metric this product will produce.
- **`tool_health(days)`** answers §15's "failed tool calls". Every Buddy tool is now built through a small factory in `buildTools` that wraps `run` and records `{name, outcome, ms}` into `ai_messages.routing -> 'tools'` — so it needed no new table. The tool definition is constructed exactly as before and the wrapper returns and rethrows whatever the tool did, so nothing about the agent loop changed. **"empty" is tracked apart from "error"**: a tool that correctly reports finding nothing is working, but one that is *always* empty is usually a permission or data problem, which is what an administrator actually wants to see.
- **One item on §15's list is deliberately not built: a list of people's unanswered questions.** `ai_conversations` is `aic_own` and `ai_messages` reaches its tenant through it — a person's conversations with Buddy are readable by that person alone, administrators included. A SECURITY DEFINER function surfacing question text to the console would quietly repeal that, and "what people asked the AI" is exactly the kind of record §33 exists to protect. The knowledge gap is reported as counts by intent instead, and the route from a bad answer to a fixed SOP stays the one the person opts into: the feedback flag, which already carries their note to the department's knowledge owner.

### Verified actions (§11) — 0064
- **"Performed" meant "we called the API and it did not throw".** In this codebase that is not the same as "it exists": an RLS-refused write **returns no error and matches zero rows** (the fourth test report's own lesson), a trigger can rewrite a column, and a row can land where its creator cannot see it. The person got a success toast and was wrong.
- `verify_ai_action(action, entity, id)` is **SECURITY INVOKER by design**: it re-reads the created row *through the caller's own RLS*, so it answers the useful question — not "is there a row somewhere" but "can the person Buddy just helped actually see what it made?" A failed check flips the action to `failed` and the person is told, instead of the toast standing unchallenged. An entity kind with no check records `found: null` and a reason — **silence must never read as success**, which is why `VERIFIABLE` in `BuddyProposals.tsx` lists only kinds that create one readable row (`bring_in`, `focus` and `war_room` deliberately have none).
- `action_verification(days)` feeds the console's "Actions checked" tile and a *Confirmed but not there* list — the fastest way to find a permission rule that is refusing writes silently.
- Verified in a rolled-back transaction as the users themselves: a visible entity → `found=true`; an unreadable one → `found=false` and status `failed`; an unknown kind → `found=null` with its reason; the summary counted 1 verified / 1 failed; an ordinary employee was refused the console reads. `platform_self_test()`: 33 passed, 0 failed.

## Buddy: proactive, specialists, the org brain and the system map (schema 0066–0068)

### Proactive intelligence (§10) — 0066
- **Buddy waited to be asked.** Everything it knows about overdue work, stalled approvals and forgotten promises was reachable — but only if somebody thought to ask. `buddy_scan(user)` notices first: overdue tasks, work due within two days, approvals sitting for over two days, promises past due, tasks waiting on somebody for a week, and a meeting within a day with no agenda.
- **The constraint that shapes it is "do not create an annoying notification machine."** Four rules: **in-app only** — a nudge is a row in `buddy_nudges`, never in `notifications`, so it cannot reach anybody's phone (the push fan-out exists and this deliberately does not use it); **deduplicated in the database** by `(user_id, dedupe_key)` with the day in the key, verified by a second scan the same day inserting nothing; **capped** at three per person per scan, twice a day on working days; and **quiet hours honoured** through the same `in_quiet_hours()` everything else uses.
- Everything a nudge reads is the person's *own* work, so `buddy_scan` being SECURITY DEFINER discloses nothing — there is no query in it that could return another person's row.
- **It feeds the card that already existed** rather than adding a second one: `BuddyHomeCard` computed three nudges in the browser from what was on the page, and server nudges now join that list, sorted so a high-severity one (somebody is blocked on you) comes first. Dismissing a server nudge dismisses it in the database, so it does not reappear on another device.

### Specialists underneath one Buddy (§12) — `consult_specialist`
- The person talks to GHL Buddy; when a question lands outside the answering persona's area it can put that question to another persona and use the reply. **No agent picker, no cluttered interface** — the only visible trace is a line in the answer saying who was consulted.
- Four things stop it being an expensive way to get the same answer twice: **one consult per answer**, hard-capped in `state.consults` rather than left to the model's judgement; **the specialist inherits the caller's own database client**, so a consult can never be a route around a permission; **it cannot act** — its toolset is built with `nested: true`, which removes `propose_actions`, memory writes and consulting again; and it runs short and cheap by construction.
- **`buildTools` does not call itself.** The reduced toolset is built by the route and handed in as `opts.makeNested` — a self-referencing function cannot infer its own return type, and the SDK's tool type is a union no hand-written alias reproduces faithfully. That was the first attempt and it fought TypeScript for nothing.

### The organisational brain (§4) — 0067
- `related_to(entity, id)` handled exactly one entity — `project` — and returned `{}` for everything else, so the traversal §4 describes existed as a stub. It now answers for **task, person, department and decision** as well, each branch gating before it reads. The project branch is byte-identical.
- **No graph engine, deliberately.** These relationships are already foreign keys, and every one has a permission predicate attached (`can_view_project`, `can_view_task`, the scope functions). A separate graph store would be a second copy of the truth with none of those checks — the classic way an "organisational brain" becomes a route around RLS.
- `why_delayed(project)` answers §4's own example. It returns **evidence, never a verdict**: what is late and by how many days, what is waiting and on whom, which approvals have been sitting, what is unassigned, when anything last moved. Buddy narrates the cause and must mark the causal part as inference — the database knows a task is eleven days late and cannot know why.

### The system map (§7) — `npm run system-map`
- Buddy has **no repository access**, and this does not pretend otherwise. `scripts/system-map.mjs` generates a structural index from the codebase — screens, endpoints, tables, database functions, cron jobs, environment variables and the `CLAUDE.md` section list, with no source code in it — and emits both `docs/system-map.md` and `src/lib/ai/systemMap.ts`. The `system_map` tool searches that constant, so Buddy can say *where* something lives instead of guessing, and its description makes it say which it is: an index can tell you something exists, never how it behaves.
- **Not stored in `ai_knowledge`**: that table holds what people wrote and approved, and a machine-generated index nobody owns does not belong in a reviewer's queue. Shipping it with the build also means it cannot disagree with the code it was generated from. Re-run after adding routes or migrations and commit both outputs. Live repository access is a separate thing and needs a GitHub token.

### What the database linter found (0068) — and the rule behind it
- **In this project a new function does not arrive ungranted.** Supabase's default privileges grant EXECUTE on every new function in `public` to `anon` and `authenticated`, so `revoke … from public` does **not** take that away — the grant is explicit, not inherited from PUBLIC. 0045 and 0059 recorded this for RPCs; 0060–0067 failed to apply it in three places:
  - Four **trigger functions** were reachable by `anon`. Not exploitable (calling one raises "can only be called as a trigger") but against the standard. **A trigger function needs no EXECUTE grant for its trigger to fire** — verified after revoking that sign-up, approval and memory-history triggers all still fire.
  - **`buddy_scan` and `buddy_scan_all` were executable by any signed-in member** — 0066's own comment claimed otherwise. Any member could have generated nudges for any colleague, or run the whole company's scan on demand.
  - **`account_approvers(org, …)` answered for any org id passed to it** — user ids only, but a cross-company answer, and it is only ever called from inside definer functions that do not need the caller to hold the privilege.
- After creating a function, check `has_function_privilege('anon'|'authenticated', oid, 'execute')` rather than assuming the revoke covered it. `get_advisors(type: 'security')` reports these as `anon_security_definer_function_executable`.
- **The performance advisories on the new tables were left alone on purpose**: unindexed `org_id` foreign keys (482 pre-existing), `auth_rls_initplan` from calling `auth.uid()` directly in a policy (250 pre-existing), and two permissive SELECT policies on `join_requests` (129 pre-existing — and two permissive policies is how an OR is expressed). These are the codebase's established patterns; fixing three instances out of hundreds would make it inconsistent, not better.

### A trap worth remembering
- **A fix applied in the same statement batch as a `raise exception` test is rolled back with it.** The `related_to` column fix was applied, verified by a test in the same call, reported as passing — and lost, because the exception that carried the results out also undid the `create or replace`. It resurfaced an hour later as the same error. **Apply a fix in one call; prove it in another.** CLAUDE.md already recorded the temp-table version of this from 0059; it applies to DDL just as much.

## /profile was a 404 that notifications linked to

- **`notify_account_change()` has sent people to a page that does not exist** since 0052: "Your account has been reactivated" / "deactivated", and since 0060 "Your account has been approved", all carry `link = '/profile'`. There was no `/profile` route — clicking the notification about your own account gave a 404. `screens.ts` has always listed `/profile` among the ungoverned paths, so the route was clearly meant to exist.

## Read aloud stopped after the first answer

- **`speechSynthesis.speaking` is not trustworthy, and the toggle was built on it.** `speak()` began with `if (synth.speaking) { synth.cancel(); return; }` — meant as "press again to stop". Chrome leaves `speaking === true` after `cancel()` (it frequently never fires `onend` for a cancelled utterance), and an utterance whose language has no installed voice reports `start` and then hangs forever. Once the flag sticks, **every later press takes the stop branch and returns, so nothing is ever spoken again** until the page is reloaded.
- Reproduced in a browser rather than reasoned about: the first utterance fired `start`, never `end`, and left `speaking: true`; a second press under the old logic produced **zero events** — silence — while cancel-then-speak fired `start` normally. That comparison is the whole bug in one run.
- The fix: track whether **we** started speaking in a ref, and `cancel()` unconditionally before speaking. Pressing the button now always does something — stop if we are speaking, otherwise clear whatever the browser thinks is happening and start fresh. A 4-second ticker resumes a queue Chrome has silently paused (it goes quiet after about fifteen seconds and reports nothing) and clears our flag if the browser finished without telling us.
- Panel close and unmount stop the voice **through the effect's cleanup**, not a branch in its body — that is what cleanup is for, and it is the only version that does not set state during an effect.
- Related, already fixed earlier: read-aloud used the *preference* language rather than the language of the reply (see the fourth test report). Both bugs were in the same function; neither was visible from the code alone.

## UI/UX audit — keyboard focus was invisible everywhere (WCAG 2.4.7)

- **Only form controls had a focus style.** `globals.css` defined `.input:focus / .select:focus / .textarea:focus` and nothing else, while Tailwind's preflight removes the browser's own outline — so every button, link, tab, menu item and toggle in the product focused **invisibly**. Somebody navigating by keyboard could tab through an entire screen with no idea where they were. Measured on the live site: a focused button reported `outline-style: none` with no ring of any kind.
- The fix is one rule, using `:focus-visible` so **a mouse click never draws a ring** — verified: clicking leaves `outline: none`, tabbing gives `solid 2px`. `:where()` keeps specificity at zero so any component can still override it without `!important`, and the colour is the existing `--brand-2` token, which is already lighter in dark mode (`#60a5fa` vs `#2563eb`) — both verified in the browser.
- The rest of the audit came back clean: no hard-coded greys (0 instances), no `<img>` without `alt`, no table missing a horizontal scroll wrapper, no horizontal overflow at 375px, `Field` associates its label by wrapping the control, and every new component has loading, empty and error states. `body` still has no `overflow` (the 0055 rule) and light mode keeps the login scrim dark so the white text outside the card stays legible.
- **Noted, not changed** — two design trade-offs rather than defects: the login hero is a 1942×809 photo in a 375×812 viewport, so on a phone `object-cover` shows about a fifth of its width and Next serves a 375px-wide variant that is then scaled to ~1950px (visible softness; fixing it means shipping a much larger image for something behind a 70% scrim); and the "Create an account" text link is a 20px-high tap target, under the 24px pointer-target guideline, which cannot be enlarged without breaking the sentence it sits in.
- **What this audit could not cover**: everything behind the sign-in. Entering a password is not something I do, so the authenticated screens — the shell, nav, all 89 pages, the new `/people/requests`, the Privacy Center memory card, the Buddy panel and the admin console — were verified by build, types and database tests but **not looked at**. They need a human-driven pass.

## Mobile: `overflow-x: clip` was hiding missing content, not preventing it

- **How this was measured.** The device toolbar is DevTools and cannot be scripted, and resizing a maximised Chrome window does nothing. A **popup window** opened from the page with `window.open(url, '_blank', 'width=390,height=844')` — triggered by a real click, so the popup blocker allows it — gives a genuine 398 × 806 CSS viewport that shares the session. It sits outside the extension's tab group so it cannot be screenshotted, but it is same-origin, so the opener can read `w.document` and measure everything. `main.scrollWidth - main.clientWidth` is the honest number: **how much of the page is cut off**.
- **Three separate blowouts, one cause.** A grid or flex item defaults to `min-width: auto` and will not shrink below its content's intrinsic width. Every `lg:grid-cols-*` grid collapses to a single implicit `auto` track on a phone, so one wide child sizes the whole track:

  | page | clipped | culprit |
  |---|---|---|
  | `/` | **317px** | `lg:col-span-2` dashboard column at 684px in a 346px track |
  | `/command` | **93px** | four `ListCard`s sharing one track, all taking the widest one's 460px |
  | `/admin?tab=ai` | **364px** | a `.card` holding a `min-w-[640px]` table, at 731px |

- **And `main`'s `overflow-x: clip` hid all of it.** That rule is right (0055 moved the guard off `body`, where it had broken sticky app-wide) — but `clip` does not scroll. There was no scrollbar, no horizontal overflow, no symptom: a third of the home page simply did not exist on a phone. `scrollWidth` on the document stayed equal to the viewport, which is why an overflow check alone reports everything as fine. **Measure `main.scrollWidth` against `main.clientWidth`, not `documentElement.scrollWidth` against the viewport.**
- **Fixed in the design system**, after fixing two instances by hand made it obvious it was a class rather than a bug: `min-width: 0` on `.card`. It removes the automatic floor, changes nothing for a card that is an ordinary block or at any width where the track is already wide enough, and lets the `overflow-x-auto` wrapper around a wide table do the scrolling — which is what should scroll on a narrow screen. The three dashboard columns keep their own `min-w-0` as well, since they are grid items in their own right.
- **Every fix was proven in the live page before it was written**: setting `min-width: 0` on the element in the running document collapsed the track (684 → 346, 460 → 346) and took `main`'s clipping to zero. Then the same measurement after deploying confirmed it.
- **Verified clean afterwards at 398px** — 0px clipped on `/`, `/my-work`, `/command`, `/admin?tab=ai`, `/admin?tab=people`, `/people`, `/people/[id]`, `/people/requests`, `/tasks`, `/projects`, `/attendance`, `/inbox`, `/chat`, `/connect`, `/leave`, `/workforce`.

## The app installs from the browser (PWA)

- **One missing line was the whole problem.** `manifest.json` was already complete — name, `start_url`, scope, `display: standalone`, 192 / 512 / maskable icons, four shortcuts — and `PushRegistrar` already registered `/sw.js` on every load. But Chrome will not treat a site as installable unless its worker **handles `fetch`**, and the worker deliberately had no `fetch` handler. So there was no `beforeinstallprompt`, no install icon in the omnibox, no "Install app" in the browser menu. Everything else had been built; the browser was never asked.
- **The handler stays out of the way.** `sw.js` now answers `fetch`, but only for top-level navigations (`req.mode === "navigate"`), and only by calling `fetch(req)` — nothing successful is ever cached. Every other request returns without `respondWith`, which hands it back to the browser untouched: API calls, RSC payloads, Next chunks, images and Supabase traffic never enter the worker. The no-stale-shell rule this file opens with is intact.
  - `event.request` is forwarded **verbatim** rather than rebuilt. A navigation request carries `redirect: "manual"`, so `fetch(req)` returns an opaqueredirect the browser follows itself. Rebuilding it would make the worker follow the redirect and then throw on `respondWith` — which would break every `proxy.ts` auth redirect in the app.
- **`/offline.html`** is the only thing cached (at install, in `ghl-one-shell-v1`), and only as a fallback for a navigation that fails. A standalone window has no address bar, so a dead navigation there has no way out. It is a static card with no company data.
  - It had to be added to the `proxy.ts` matcher exclusions: governed, it would redirect to `/login`, and **`cache.add` throws on a redirect** — the fallback would silently not exist on the one occasion it is needed.
- **`beforeinstallprompt` fires before React mounts.** A listener registered in an effect misses it on a cold load and the install option silently never appears. `src/components/shell/InstallApp.tsx` registers at **module scope** and components read the captured event through `useSyncExternalStore` (server snapshot `"none"`, so nothing renders during hydration). The event is single-use — it is cleared on `prompt()` whatever the person chooses.
- **Two places, neither of them in the way.** `InstallAppMenuItem` in the topbar user menu at every width, and `InstallPrompt` — one dismissible line above the page content, `lg:hidden`, 30-day snooze in localStorage, the same external-store shape as `PushOptInPrompt`. ## A cast hid a dead Buddy tool — and the check that now catches it

- **`org_who_owns` had never worked.** The tool called `who_owns` with `{ q }`, but the function is `who_owns(p_q text)`. PostgREST resolves an RPC by its parameter **names**, so this was not a bad value — it was a different function that does not exist. Proven against the live API: `{"q":…}` returns **404 `PGRST202`** *"Searched for the function public.who_owns with parameter q … but no matches were found in the schema cache"*, while `{"p_q":…}` reaches it. The tool answered `"not available: …"` every single time, and because that string is a normal tool result, nothing ever looked broken.
- **The generated type was right all along** — `Args: { p_q: string }`. What silenced it was `as never` on the argument object. A cast on the argument is a cast on exactly the thing that needed checking.
- **`npm run test:contract`** (`scripts/db-contract.mjs`) now reads every `.rpc()` and `.from()` in `src/` **as text** and checks it against `database.types.ts` — function exists, every top-level key is a real parameter, table exists. Reading text rather than types is the point: a cast cannot hide a call site from it.
  - Top-level keys only, found by **brace-matching**, so a `p_details` payload or a `p_context` blob is stepped over rather than read as parameters. A naive `[^}]*` regex reports those nested keys as errors — that was the first draft, and it produced a dozen false positives.
  - A key is only a key in **key position** (start, or after a top-level `,` / `;` / newline). Scanning for "word followed by a colon" reads the middle of a ternary (`p_from: a ? b : c` → a phantom key `b`) and misses `p_user?: string` entirely, because the colon is behind the `?`. A multi-line TS object type separates properties by newline alone, so a newline opens a key position too — but one opened that way must be followed by a colon, or a wrapped JS value would look like a key.
  - **Verified it fails before trusting it to pass**: a probe file containing `who_owns({ q })`, an unknown function and an unknown table produced exactly three errors, while `has_perm({ p_perm, p_user })` and `from("tasks")` passed. Then 362 rpc and 1155 table call sites clean.
  - Wired into `npm run check` **ahead of** `verify`, which exits early without a `SUPABASE_SERVICE_ROLE_KEY` and would otherwise make the offline checks unreachable.
- **The other fifteen `as never` rpc calls were checked by hand** against the live catalogue — `ingest_*`, `set_connect_settings`, `create_breakouts`, `board_to_project`, `log_access_event` and the Buddy tools all name their parameters correctly. `who_owns` was the only one.

## The server was in UTC and the people are in IST (React #418)

- **Every signed-in page load of Home and My work logged a hydration error.** `greeting()` read `new Date().getHours()`. A client component is server-rendered too, so that ran twice — once in Netlify's UTC process and once in an IST browser. At 20:14 IST (14:44 UTC) the HTML said **"Good afternoon, Abe"** and the client rendered **"Good evening, Abe"**: React error #418, a server/client *text* mismatch, on every load.
- **Measured, not guessed.** Fetching the page and diffing the server HTML's `main` against the live DOM gave `onlyServer: ["Good afternoon, Abe", "…"]` against `onlyClient: ["Good evening, Abe", …]`. `/command` came back `onlyServer: []` and, on a *freshly cleared* console, logged nothing — the earlier hits there were stale buffer from the previous navigation. **Clear the console buffer before attributing an error to the page you just opened.**
  - That diff is only evidence for text the client renders *at hydration*. Everything else in `onlyClient` was effect-loaded (the AI summary, the workspace name, the clock) and legitimately differs from the server HTML — it is not a mismatch. `WorkspaceSwitcher` and `ClockWidget` both render their placeholder (`Workspace`, `…`) on the server **and** on the first client render, then fill in from an effect, which is the correct shape.
- **Fixed in the code, not in the deployment.** `APP_TIME_ZONE` (`NEXT_PUBLIC_APP_TIMEZONE`, default `Asia/Kolkata`) and `zonedNow()` in `utils.ts` read the wall clock in one named zone via `Intl.DateTimeFormat(...).formatToParts`, so both runtimes compute the same hour. Proven by running the same expression under `TZ=UTC`, `TZ=Asia/Kolkata` and `TZ=America/New_York`: all three return hour 20, "Good evening", 2026-9-18. `NEXT_PUBLIC_` matters — the value has to be identical on both sides, so it must be in the client bundle.

  - It is **only** for "what is the time right now". A timestamp from the database is still rendered in the viewer's own local time, which is what `fmtDate`/`relDate`/`ago` should do.
- **`todayLabel()`** replaces `fmtDate(new Date())` in the four page-header eyebrows. That one was latent rather than visible: it only mismatched between 00:00 and 05:30 IST, when UTC is still on the previous date.
- **`TZ=Asia/Kolkata` is also set on both Netlify sites**, which is a separate correctness fix rather than a duplicate: it puts server-side date windows (`/command`'s and Home's `startOfDay`, every `isToday`) on the same day boundary as the people using them and as the pg_cron schedules, which have always been written in IST. ## Push now fires from ghl-one — and a warning about reading Netlify secrets

- **`push_config.hook_url` moved to `https://ghl-one.netlify.app/api/hooks/push`.** Which site owns the fan-out is a live decision, not a code one: `notification_push_fanout()` posts to whatever that column says, so switching sites is one `update` and needs no deploy.
- **Verified end to end, twice, against real traffic** — insert a notification, watch `net._http_response`, then delete the test row. The new endpoint returns `200 {"ok":true,"sent":1,"failed":0,"pruned":0}`, and `POST /api/hooks/push/<wrong secret>` on ghl-one answers `403 {"error":"forbidden"}`, so the route is live and still authenticating.
- **The Netlify API redacts `is_secret` environment variables, and the redaction looks like a value.** `getEnvVars` returns `****************` plus the last four characters — a 20-character string. Hashing that and comparing it to `push_config.hook_secret` (48 characters) "proved" a mismatch that would have meant push had never worked. It was wrong. **Never compare, hash or length-check a Netlify env value without checking `is_secret` first**; the only honest evidence about a secret is whether the thing using it succeeds. Here that evidence was `net._http_response`, which had been returning `ok:true` all along.
  - A second trap in the same query: `select left(max(content), 300)` picks the **lexicographically greatest** body, and `{"ok":true` sorts above `{"ok":false`. One success among many failures would look like total success. Group by the body instead of taking `max()` of it.
- **`timeout_milliseconds` is now 15000, up from 5000 (0069).** The first call after the switch spent 4.83 s in request/response against a cold function and pg_net gave up at 5 s — but the push had already been sent: `push_subscriptions.last_used_at` was stamped 6 s after the insert with `failure_count` still 0, and the warm call straight after returned 200 in under a second. The timeout never lost a notification; it wrote rows into `net._http_response` that look like failures and are not. `net.http_post` queues and returns immediately, so the wait is the background worker's and never the inserting transaction's — raising it costs the writer nothing.
- The trigger on `notifications` is named **`notifications_push`** (`notification_push_fanout`, AFTER INSERT). `create or replace function` does not detach a trigger, but check the real name before asserting a trigger is gone — guessing it and getting 0 looks exactly like a detached trigger.

- After the go-live reset, 12 blobs (~2.4 MB) were left with no owning row: 2 in `chat`, 2 in `files`, 1 in `hr`, 7 in `live`. All are gone; every bucket now reports 0 objects / 0 bytes. **`avatars` was not touched** and still holds 5 objects — both profile pictures still serve `200 image/jpeg`.

## Dictation duplicated the sentence, and Buddy never knew to answer in Tamil

Three separate defects behind one report ("the query repeats itself, regional language doesn't work, 504").

- **Dictation glued every hypothesis of one sentence together.** `BuddyComposer` set `continuous = true` and built the text by concatenating every entry of `event.results` — which is what the spec implies, since a result is one utterance and an interim result replaces its entry in place. **Chrome on Android does not do that**: each new hypothesis of the SAME sentence arrives as a NEW entry, and none is final until the end. Speaking *"எனக்கு ஒரு ஆன்லைன் பிசினஸ் வேணும்"* (33 characters) produced **111** — `எனக்குனக்கு ஒருனக்கு ஒரு ஆன்லைன்என்னக்கு ஒரு ஆன்லைன்…`, the sentence eating itself. That paragraph then went to the model as the question, which is what returned 504. Malayalam produced the identical shape.
  - **The rule now: one session is one sentence (`continuous` off), and only the LAST entry is read.** Correct under both behaviours — an engine that replaces in place has exactly one entry, one that appends puts its most complete hypothesis last. Nothing accumulates *inside* a session, so no engine quirk can duplicate anything; sentences accumulate across sessions in state this app owns, and the composer starts each next session itself. `continuous` was never honoured on Android anyway.
  - **The transcript logic is in `src/components/ai/dictation.ts`, apart from React and from any timer, because it cannot be verified by reading it.** `npm run test:dictation` (`scripts/dictation-cases.mjs`, in `npm run check`) replays both engine shapes — the real Tamil and Malayalam hypothesis streams from the report — and asserts 9 outcomes. **Proven to fail first**: the old reader was re-run against the appending stream and reproduced the screenshot's exact 111-character string.
  - Two traps while writing it: a self-referencing `useCallback` (`begin` restarting itself) is *used before declared* — it goes through a ref; and a restart must be scheduled, never called synchronously inside `onend`, which throws `InvalidStateError`. `no-speech` keeps the mic on (it is a pause for thought) while every other error stops it, and four instant empty sessions in a row stop it too — without that, a blocked microphone is a hot loop.
  - **Sending now ends dictation.** It did not, so the next result restored the text that had just been sent.
- **Nothing had ever told Buddy which language to answer in.** `BUDDY_SYSTEM` contained no language rule; the only lever was the composer dropdown, which sent one line — *"Answer in Tamil."* — at the end of a page of English context, and lost to it. Ask in Tamil with the dropdown on English and the reply came back in English. The rule now lives in the **cached system block**, so it costs nothing and covers the four surfaces that have no dropdown at all (`@GHLBuddy` in chat, board AI, live invite, room AI): answer in the language *and script* the message was written in, never transliterated, the English context block is not a language instruction, and the `[confidence: …]` marker is never translated — `parseConfidence` anchors on it. The dropdown is now an explicit override rather than the only signal.
- **Every non-Latin question paid the router hop twice.** Every rule in the orchestrator is an English `\b`-anchored pattern, so a Tamil, Malayalam or Hindi message scores exactly zero and *always* falls through to the model classifier. `routeBuddy` was awaited before the profile read, which does not depend on it; they now run together. Note this the next time a rule is added: **word-boundary keyword rules cannot score a non-Latin script at all**, so the classifier is not a fallback for these languages, it is the only path.
- **A gateway timeout never reaches the route**, so there is no `error` in the body and the person got the bare *"AI request failed (504)"*, which reads as a broken product rather than an answer that ran long. `callAI` now maps 408/502/504 to plain language. `maxDuration = 120` in the route is a Vercel-ism — **Netlify does not honour it**; the synchronous function ceiling is a project setting (Pro: up to 26 s), so raising it is done in the Netlify UI, not in code.
- **Not fixed, deliberately**: `useRecorder.ts` reads `event.results` the same way for live meeting transcripts. Its shape differs — it iterates from `resultIndex` and only commits `isFinal` entries, so the Android behaviour would duplicate *transcript lines* rather than mangle a sentence — and it is a different surface that was not reported and could not be verified here. Recorded rather than papered over.
