# GHL ONE — Company Operating System for GHL India Ventures

Next.js 16 (App Router, `src/`), React 19, Tailwind v4, Supabase (project `rarlrohsybktcheyrhiv`).
Positioning: *One Company. One Workspace. One Source of Truth.*

## Conventions (read before writing code)
- **Auth/session**: server pages call `getSession()` from `@/lib/session` (redirects to /login or /pending). Client components use `useSession()` from `@/components/providers/SessionProvider` → `{ profile, departments, people }`.
- **Supabase**: server → `createClient()` from `@/lib/supabase/server`; client → `createClient()` from `@/lib/supabase/client`. Types in `@/lib/database.types` (generated). Row/enum aliases + label maps + helpers in `@/lib/utils` (`Task`, `Project`, `STATUS_LABEL`, `PRIORITY_TONE`, `fmtDate`, `relDate`, `ago`, `isManagerPlus`…).
- **UI primitives**: `@/components/ui` — `Button`, `Pill`, `Avatar`, `AvatarStack`, `Card`, `CardHeader`, `Input`, `Textarea`, `Select`, `Field`, `SearchInput`, `Modal` (`side` for drawer), `Tabs`, `EmptyState`, `Spinner`, `Skeleton`, `Kbd`, `Stat`, `Progress`, `Menu`/`MenuItem`, `PageHeader`, `useToast()`.
- **Pickers**: `@/components/pickers` — `PersonPicker`, `DepartmentPicker`, `PriorityPicker`, `StatusPicker`, `ClassificationPicker`, `ProjectPicker`.
- **Task bits**: `@/components/tasks/TaskBits` — `StatusPill`, `PriorityPill`, `WaitingPill`, `DueLabel`, `PersonChip`, `TaskRow`. `@/components/tasks/QuickTaskForm` creates tasks.
- **Styling**: CSS tokens in `globals.css` (`var(--bg-elev)`, `var(--line)`, `var(--fg-muted)`, tones `.tone-*`, `.card`, `.btn`, `.input`, `.pill`, `.page`, `.h1/.h2/.h3`, `.eyebrow`, `.text-muted`). Golden-ratio spacing `--s1..--s7`. Dark mode = `.dark` on `<html>`; use tokens, never hard-coded greys. Mobile first: no horizontal overflow; bottom nav is 56px on <lg.
- **Routes** live under `src/app/(app)/…` (inside the shell). Auth pages outside: `/login`, `/pending`, `/auth/*`. Proxy at `src/proxy.ts` protects everything else.
- **Data rules** are enforced in Postgres (RLS + triggers). Notifications, task history, audit logs, calendar entries and project channels are created by triggers — do not duplicate in the client. RPCs: `search_all`, `company_pulse`, `department_health`, `workload`, `open_dm`, `mark_channel_read`, `my_unread_counts`, `task_from_message`, `create_project_from_template`, `create_delegation`, `related_to`.
- Roles: super_admin > director > executive > department_head > manager > team_lead > employee > intern > consultant > vendor > guest. Helpers `isAdminRole`, `isManagerPlus`, `isLeadPlus`, `isInternal`.
- Never run `next build` while `next dev` is running. Verify in the browser, then commit → push → deploy.

## Intelligence (Phase 2)
- Server-only AI layer in `src/lib/ai/` (`client.ts` = Anthropic SDK wrapper `complete()` / `extract()` + usage logging; `context.ts` = permission-safe context builders that ALWAYS use the caller's RLS-scoped Supabase client; `prompts.ts` = stable cacheable system prompts; `route.ts` = `withAI()` auth/error wrapper + summary cache helpers). Routes under `src/app/api/ai/*` (ask, brief, project-summary, meeting-extract, extract-tasks, delegate-parse, catch-up, risks, search, status). Client code uses `callAI()` and types from `@/lib/ai/types` and must handle `.disabled` (no `ANTHROPIC_API_KEY`).
- Model: `claude-opus-5` (override with `AI_MODEL`). Cheap routes use `effort: "low"`. The AI never executes actions — it proposes; humans confirm in the UI.
- Cached outputs live in `ai_summaries`; usage in `ai_usage` (admin-visible).

## Automation (Phase 3)
- Engine lives in Postgres (`0006_automation.sql`): `automations` (WHEN trigger_type + trigger_config → IF conditions → THEN actions; see `run_automation_action` for action JSON) fired by AFTER triggers via `fire_automations()` with a depth guard (max 2); `automation_runs` log; `schedule` triggers and the escalation ladder (`escalation_rules`) run on pg_cron (`run_scheduled_automations` every 5 min, `run_escalations` every 15 min, digests daily/weekly 08:30 IST). Recurring tasks: `tasks.recurrence` → next occurrence spawned on completion. Handoffs: `handoffs` table + trigger moves/assigns the task. Outgoing webhooks/Slack via `pg_net`; incoming via `/api/hooks/{token}` → `ingest_webhook()`; personal ICS feed via `/api/calendar/{token}.ics` → `calendar_feed()`.
- Template variables for automation text: `{{title}} {{assignee_name}} {{owner_name}} {{project_name}} {{department_name}} {{due}} {{link}} {{status}} {{priority}} {{actor_name}}`.

## Migrations
`supabase/migrations/*.sql` are the source of truth and are applied to the remote project via the Supabase MCP (`apply_migration`). Keep them additive.

## Multi-company platform (0022_platform.sql)
- **Hierarchy**: *platform* → *company (tenant)* → *department* → *team* → *person*. A tenant **is** an `organizations` row; `organizations` now carries `tenant_code`, `status` (trial|onboarding|active|suspended|read_only|archived|closed|pending), `plan`, `industry`, `country`, `timezone`, `email_domain`/`restrict_to_domain`, `custom_domain`/`domain_verified`, `logo_url`/`accent_color`/`welcome_message`, `terminology`, `limits`, `onboarding_stage`, `mfa_required`, `retention_days`.
- **Identity**: one person, many `memberships` (user_id + org_id + role + status). `active_workspace` holds the tenant they are currently in and `current_org()` resolves to it *only* when they have an active membership there or platform authority — otherwise to their profile's org. Switching is `set_active_workspace(p_org, p_reason)`; the picker list is `my_workspaces()`. **Never mix tenants in one view**: after switching, `router.refresh()` so every server component re-reads.
- **Platform roles** (`platform_admins.role`, `platform_role()`): `platform_super_admin` (owner — the only one who may edit `platform_admins`/`platform_assignments`/`platform_features`), `platform_ops` (create companies, change status), `platform_security`, `platform_support` / `platform_billing` / `platform_developer` (reach only the tenants listed in `platform_assignments`). `platform_can_touch(org)` is the gate; `platform_admin_invites` recognises a platform person by email before their first login. Platform staff are **not** members of any tenant.
- **Break-glass** (`start_break_glass` / `end_break_glass`): platform staff see administrative metadata by default; reading a tenant's *content* needs an open session with a written reason (≥12 chars), a justification category, a scope (`configuration`|`content`|`full`) and an expiry (5–480 min). Opening one notifies the company's own admins, writes `platform_audit_logs` + `security_events`, and shows a persistent banner in the shell until it is closed. The company's own door is `grant_support_access` / `revoke_support_access` (`/admin?tab=support`).
- **Company lifecycle**: `create_company(...)` (owner/ops only) → departments, channels, features, onboarding checklist, admin invite and a private onboarding room; `set_company_status(org, status, reason)` refuses `active` while `company_go_live_blockers(org)` is non-empty; `company_setup_health(org)` drives every progress bar. **Deletion is never offered** — only Suspend / Read-only / Archive, each with a typed reason.
- **Features**: catalogue in `platform_features`, per-tenant overrides in `org_features`. Read with `org_feature_enabled(key, org)`; write **only** through `set_org_feature(org, key, enabled, limit)` (audited).
- **RULE — every new table must carry `org_id` and an org-scoped policy** (`using (org_id = current_org() and …)`). A table that reaches its tenant only through a parent must be listed deliberately; `tenant_isolation_report()` flags anything missing and `tenant_isolation_probe(other_org)` (SECURITY INVOKER, runs under the caller's RLS) proves a second company reads zero rows. Both are the release check, surfaced at `/platform` → Isolation and on each company's Security tab.
- **UI**: `/platform` (command center), `/platform/[id]` (one company: Overview · Admins · Departments · Usage · Features · Security · Onboarding · Audit · Configuration), `/platform/new` (nine-step onboarding wizard). Components in `src/components/platform/*` (types + label maps in `lib.ts`). Every platform page re-checks `is_platform_admin()` server-side and `notFound()`s — hiding a nav item is never the control. `<WorkspaceSwitcher/>` in `AppShell` is the mandatory always-visible tenant indicator and turns orange (“Administrative mode”) when the viewer is in a company as platform staff.

## Web push + PWA (schema 0025_push.sql)
- **Why**: an in-app notification reaches nobody who is not already looking at a tab. Push is a *second* delivery channel — the `notifications` row stays the source of truth and every push failure is silent.
- **Flow**: any `insert into notifications` → AFTER INSERT trigger `notification_push_fanout()` → `net.http_post` to `push_config.hook_url || '/' || hook_secret` (same pg_net pattern as the webhook action in `0006_automation.sql`) → `POST /api/hooks/push/[token]` → `sendPushToUser()` → the browser's `/sw.js`.
- **Authentication — no service-role key.** Postgres calls the hook with no session, so the route authenticates with `PUSH_HOOK_SECRET` (constant-time compare, header or path) and every privileged read happens *inside Postgres*, in SECURITY DEFINER functions that re-check that same secret against `push_config.hook_secret`: `push_notification(secret, id)` (the row, as JSON), `push_targets(secret, user, org, kind)` (`{ok, quiet, subs}` — applies `in_quiet_hours()`, skipped for `kind in ('critical','action_required')`, and the org scoping, limit 25), `push_settle(secret, dead, shaky, delivered)` (prune / strike-out at 10 / stamp). Each returns a benign empty value on a wrong secret and never reveals whether a user or row exists, so `execute` is granted to `anon, authenticated` — the secret *is* the credential. The app itself runs on the anon key only; **do not reintroduce `SUPABASE_SERVICE_ROLE_KEY`** to "simplify" this.
- **Schema**: `push_subscriptions` (user_id, `org_id` + `push_subscription_org_default()` trigger mirroring `notification_org_default()`, unique endpoint, p256dh, auth, user_agent, last_used_at, failure_count; RLS = own rows for all operations + org-scoped SELECT for `is_admin()`/`security.manage`); `push_config` (one locked row: `hook_url`, `hook_secret`, `enabled` — **RLS on with no policies**, so a member can never select the secret). Writes go through `save_push_subscription()` / `remove_push_subscription()` (SECURITY DEFINER — a shared browser can hold another person's row on the same endpoint).
- **Tenant scoping**: a device belongs to the workspace it was registered in. `PushRegistrar` (mounted in `AppShell`) silently re-posts the subscription on every load so `org_id` follows a workspace switch, and the fan-out only targets subscriptions matching the notification's `org_id`. Company B never rings a device currently signed into company A.
- **Client**: `src/lib/push/client.ts` (`usePush()` → `{ ready, supported, permission, subscribed, blocked, subscribe, unsubscribe, message }`). **Permission is never requested on load** — only from a click. `blockReason()` distinguishes unsupported / iOS-without-install / denied / no-VAPID-key, each with a plain-language message in `BLOCK_MESSAGE`.
- **UI**: `PushOptInPrompt` (one dismissible line in `NotificationsPanel`, 30-day snooze in localStorage) and `PushOptIn` (the real toggle, in the profile's Notifications card next to `NotificationSettings`). Both in `src/components/notifications/PushOptIn.tsx`.
- **Service worker**: `public/sw.js` — push-only, no offline cache. A ring notification (`entity_type = 'live_room'` with `?invite=` in the link) gets `requireInteraction` plus **Accept** → `/live/<room>?invite=…&accept=1` and **Decline** → `POST /api/push/decline` (→ `respond_live_invite`). `pushsubscriptionchange` re-subscribes and re-posts. `sw.js` is excluded from the `proxy.ts` matcher; `/api/hooks/push/…` is already covered by the `/api/hooks/` anon allowlist.
- **Env**: `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `PUSH_HOOK_SECRET`. Missing any of them degrades to "push not configured" / "no-secret" — nothing throws. **`SUPABASE_SERVICE_ROLE_KEY` is NOT required — nothing under `src/` reads it and the running app never holds one** (the only consumer is `scripts/verify.mjs`, the out-of-band DB self-test in `docs/TESTING.md`). A service key bypasses every RLS policy in the product, which is the opposite of what tenant isolation is for.
- **PWA**: `public/manifest.json` (standalone, shortcuts, PNG + maskable icons in `public/icon-192.png`, `icon-512.png`, `icon-maskable-512.png`, `badge-96.png`). iOS delivers push only to an installed PWA — the opt-in says so instead of failing silently.

## Access control — Platform Owner, roles and permissions (schema 0035–0036)
- **The rule**: no permission = no access, and *admin is a role, not an amount of power*. `has_perm(perm, user)` is the single source of truth; `src/lib/permissions.ts` (`can`, `canAny`, `requirePermission`) and `usePermission`/`usePermissions`/`<Can>` both go through it. UI helpers hide controls — they are **never** the control. Every protected route, RPC and query is still checked in Postgres.
- **Precedence** (`has_perm`, highest first): platform owner reserved authority → active membership → **explicit individual DENY** → explicit individual ALLOW → employment status (probation/notice/suspended) → system roles → department default → level default → company super admin *bounded by `company_admin_limits`* → deny. The old first line was `if role = 'super_admin' then return true`, which made an explicit deny unwritable; individual rules are now evaluated first. Verified behaviour-identical against the previous logic across every user × permission (731 combinations, 0 mismatches) before anything was built on it.
- **Platform owner** = `platform_admins.role = 'platform_super_admin'`. `is_platform_owner()` / `is_platform_owner_user(uuid)`. Holds platform authority outright — the one unconditional branch, so the owner cannot lock themselves out. Keys prefixed `platform.` never resolve inside a company for anybody.
- **`permissions`** is the catalogue (key, label, description, `grp`, `risk` standard|elevated|high, `requires[]`, `platform_only`). Add a new key here or it will not appear in the studio, in `effective_permissions`, or in any risk/dependency warning.
- **`company_admin_limits`** caps what one company's own administrators may hold and hand out (`admin_ceiling(org)`; null = unrestricted, which is every existing company). Only the platform owner writes it; a company may read its own ceiling.
- **Nobody grants what they do not hold**: `can_manage_permission()` + BEFORE triggers on `permission_overrides`, `system_roles` and `role_defaults`. You must administer permissions, hold the key yourself, stay inside the ceiling, and have `security.manage` for high-risk keys; you cannot grant yourself anything. `guard_platform_admins` stops a tenant touching platform staff and stops the last owner deleting or demoting themselves. All authority changes land in `permission_changes` (before/after/actor).
- **Reads**: `explain_permission(user, perm)` returns the whole precedence chain (the "why can/why not" answer); `effective_permissions(user)`; `preview_user_access(user)` / `preview_role_access(role)` are **simulations, never impersonation**; `permission_holders(perm)` answers "who can see this?"; `role_change_impact(role, perms)` gives the diff, high-risk callout, dangling dependencies and affected-people count *before* a save; `access_review_board()` lists high-risk holders, temporary grants, acting roles and authority left on people who have gone. `system_role_versions` snapshots every role change and `restore_system_role()` rolls one back.
- **Guards must fail closed.** `can_review_access` first returned NULL for an unauthenticated caller (`p_user = auth.uid()` is NULL), and `if not NULL then raise` never fires — the guard fell open. Coalesce every guard to false. Equally: revoking an RPC from `anon` does nothing on its own, because the privilege comes from the PUBLIC grant a new function receives by default — `revoke … from public` **and** `from anon`, then grant `authenticated` back.
- **UI**: `/platform/access` (`src/components/access/*`) — Roles (action matrix + diff + impact + version history), People (effective access, per-key allow/deny/expiry, "Why?"), Permissions (catalogue + "who has this"), Company limits (owner only), Access review. Re-checked server-side and again inside every RPC.

## RBAC — granular permissions and the Company Super Admin (schema 0040–0042)
- **Module × action catalogue (0040)**: the catalogue was broad verbs (`view`, `create`, `edit`, `delete`) plus a few `<module>.manage` keys, which cannot express "may edit the wiki but not delete people". It is now `module.action` — `people.view`, `files.upload`, `announcements.publish`, `roles.assign` — 125 keys, of which 76 are granular. **Every granular key records the broad key it refines in `permissions.legacy_alias`, and `has_perm` resolves the key OR its alias.** A role written against `view` therefore still satisfies `people.view`, `wiki.view` and `files.view`: the split grants nothing new and takes nothing away. Verified behaviour-identical across every user × every pre-existing key (833 combinations, 0 mismatches) before anything was built on it. `permissions.module` / `.action` are informational; authorisation is always by key.
- **Precedence is unchanged**, and the exact key beats its alias: an explicit deny on `people.export` is not undone by an inherited allow on `export`. Employment-status restrictions (probation/intern lose download, share, export) follow the alias too, so `files.download` is blocked for the same people `download` always was.
- **Adding a key**: insert it into `permissions` with a `legacy_alias` pointing at the broad key that used to govern it, or null if it governs something genuinely new. The Access Studio's role matrix renders straight from the catalogue (`byGroup`), so a new key appears in the editor, in `effective_permissions`, and in the risk/dependency warnings with no front-end change.
- **`company_super_admin` (0041) is a security role, not a level.** "Runs this company" used to mean `profiles.role = 'super_admin'` — a hierarchy level, which is organisational identity. **Job title, hierarchy level and security role are three separate things and none of them may be derived from another**: `designation` is a job title and is display-only, `profiles.role` is where someone sits in the chain of command, and authority comes from `system_roles` held through `user_roles`. `is_company_super_admin()` is the check; it is bounded by `admin_ceiling()` exactly as the level branch is, and `platform.%` keys never resolve for it. Existing level-super-admins were backfilled once so nobody lost access; the two move independently from here. Never write `if role = 'super_admin'` (or anything reading `designation`) into an authorisation path — `test_access_control()` fails the build if `has_perm` ever mentions a job title.
- **Two guards that were missing (0041)**: `trg_guard_user_role` — nobody may *assign* a role granting a permission they do not hold themselves, nobody may give themselves a role, and a role containing a high-risk key needs `security.manage` to hand out. Deliberately narrower than `can_manage_permission()`, which asks "may you edit the catalogue" and would have blocked HR from making somebody an Employee. `trg_last_super_admin_profile` / `trg_last_super_admin_role` — a company can never be left with no administrator, counting both routes to the authority, refusing with the message the brief specifies.
- **Fixed in passing (0041)**: `log_permission_change()` read `new.perm` outside the branch that knows the column exists. plpgsql resolves a record field against the row's real composite type before the surrounding `CASE` picks a branch, so on `system_roles`, `role_defaults` and `company_admin_limits` it raised `record "new" has no field "perm"` — **creating a security role or saving a level default had been failing outright**. Read a record field only inside the branch whose table has it.
- **`access_control.view`** names the Access Control screen and refines `security.manage`, so a company can let somebody review who holds what without letting them change it. Both the nav item and the page gate accept either key; the page still re-checks server-side and every RPC re-checks in Postgres.

## Permission scope — own / team / department / company (schema 0043)
- **`has_perm` answers *may you*; scope answers *over whom*.** `permission_scopes` narrows a permission's reach; it never grants one and never denies one. With no rule configured the answer is `company`, which is what the system already did, so the table is inert until somebody deliberately narrows something.
- **Why it must only narrow**: authority in this codebase does not all come from `has_perm`. `profiles`' update policy grants on `is_manager_plus() OR is_hr()`, and managers/directors hold no `people.edit` at all. A scope check that answered "false — you hold no such permission" would have taken profile editing away from every manager on deploy. It answers `company` for them instead (no opinion) and the existing gate stands.
- **Resolution**, most specific first, mirroring `has_perm`: `user → role → department → level → default → company`. The first source with a rule decides; *within* one source the **widest** rule wins, because holding two roles should union their reach, not intersect it. `permission_scope(perm, user)` returns `{scope, department_ids, source}`; `in_scope_user(perm, target)` and `in_scope_department(perm, dept)` are the thin predicates to use in policies. `department_ids` empty = "their own department", non-empty = those named departments (the brief's SELECTED DEPARTMENTS).
- **Enforced today in exactly one place**, and deliberately so: `profiles`' `profile_admin_update` policy now also asks `in_scope_user('people.edit', id)`. That is RLS — typing an id into a request is checked by the same rule — and it closes a real over-grant where a Design manager could edit an IT employee's record. Verified 0 permission drift across 2,125 user × key combinations, and that a manager holding no `people.edit` still reaches everyone.
- **Wiring more surfaces**: add `and in_scope_user('<perm>', <owner column>)` (or `in_scope_department`) to that table's policy. Do not filter in a server query instead — a hidden row is not a control. Resource-level scope for tasks, projects, files, the wiki and chat is wired as of 0047/0049; `can_view_task` / `can_view_project` / `can_view_channel` and the `files_read` / `wiki_read` policies are the controls there.

## Audit records outlive the people in them (schema 0044)
- `audit_logs.actor_id` pointed at `profiles(id) ON DELETE SET NULL` while the table carries an append-only trigger. The two contradicted each other, so **deleting anyone who had ever done something auditable failed** with `audit_logs is append-only` — offboarding hid it by deactivating rather than deleting. The log now stores `actor_label` (filled by a BEFORE INSERT trigger, so no call site changed) and has **no foreign key to profiles**: who acted is a historical fact, not a live pointer. Append-only is untouched.
- Corollary for any new audit-shaped table: record the actor's name at write time and do not make the row depend on the account still existing.

## Role-level deny, and why "why?" can no longer lie (schema 0046)
- **`system_roles.denied_permissions`** takes a permission away from everyone holding the role. It mirrors the `screens` / `denied_screens` pair the same table already uses, so it is the schema's own idiom rather than a new mechanism. Deny beats allow, as everywhere else here: an explicit deny on any held role outranks an allow on **another** held role, the department default and the level default.
- **It sits below the company-super-admin branch on purpose.** If a role could bind the company's top administrator, handing them a restrictive role would be a way to neuter the only person who can undo it — and the last-Super-Admin guard would not catch it, because they would still *hold* the role while being unable to use it. To bind a company super admin, use an individual override or the platform owner's `company_admin_limits` ceiling. Both are deliberate, visible acts.
- **Aliases resolve correctly in both directions**: denying broad `delete` also denies `tasks.delete` (the overlap catches the alias), while denying `tasks.delete` leaves broad `delete` alone (the broad key's `keys` array does not contain the narrow one). Same `&&` operator as allows, so the two tiers cannot disagree about what a key covers.
- **The precedence chain, complete** (highest first): platform owner → active account → `platform.*` never resolves in a company → individual DENY/ALLOW (exact key, then alias) → employment status → company super admin *bounded by the ceiling* → **role DENY** → role allow → department default → level default → super-admin level *bounded by the ceiling* → deny.
- **`explain_permission` no longer computes its own verdict — it returns `has_perm`'s.** 0040 taught `has_perm` to resolve a granular key through its alias and 0041 gave it the company-super-admin branch; `explain_permission` learned neither, so it answered "nothing grants this" for all 76 granular keys while `has_perm` allowed them. Roughly 1,200 wrong "why" answers, on the screen administrators trust when deciding whether someone's access is correct. The chain now explains and `has_perm` decides, so they cannot disagree about the answer again — the worst a future change can do is leave the *wording* behind. `test_access_control()` asserts the verdict still comes from `has_perm`, and also flags any role that both grants and denies the same key (deny wins, so the grant is dead config).
- **UI**: the role matrix is tri-state — click cycles inherit → allow → deny. "Inherited" is not "no access", and the tooltip says so: the key can still arrive from a department, a level or another role. Saving writes both arrays; version history and `restore_system_role` carry the denies, so restoring a version cannot silently drop them.

## Resource scope for tasks and projects (schema 0047)
- **`task_in_scope(task)` / `project_in_scope(project)`** are consulted by `can_view_task` / `can_view_project`, which are the RLS controls *and* what `search_all` filters by — so a narrowed reviewer cannot reach a task by typing its id or by searching its title. Same contract as people scope: they only ever narrow, and with no rule configured `permission_scope` answers `company` and both return true. Verified by counting what all 16 active people could see before and after: 332 task views, 15 project views, unchanged, 0 people affected.
- **Levels**, mapped onto what the tables record (neither has `team_id`, so team resolves through the people involved): `own` = named on it in any capacity (assignee, owner, creator, delegator, approver, waiting-on, collaborator) or, for a project, owner/creator/member — the brief's "assigned projects"; `team` = own plus anything whose assignee or owner shares your team; `department` = own plus the row's own department (or the named departments), with a task's missing department falling back to its assignee's, so unfiled work cannot escape a department-scoped reviewer; `company` = everything.
- **"Own" is the floor for every narrower scope.** Work addressed to you personally never falls out of your reach because somebody narrowed your department, so `department` returns own ∪ department. When testing, this is why a department scope can legitimately return the same count as `own`.
- **Performance**: these run once per row inside RLS, so `permission_scope` short-circuits on one indexed probe (`permission_scopes_lookup_idx`) when the company has no rule for the key — the overwhelmingly common case — instead of walking all five precedence sources.
- **Scope is only real where a control consults it.** `scope_enforced_permissions()` is the list — today `people.edit`, `tasks.view`, `projects.view`, `files.view`, `wiki.view`, `chat.view` — and `test_access_control()` fails if a scope rule exists on any other key, because a rule that narrows nothing while looking like a control is worse than no rule. Extend that function whenever you wire a new surface, and a second check asserts `can_view_task` / `can_view_project` still call their predicates at all.
- **UI**: the "Reach" card under a role's permission matrix (`RoleReach` in `RoleMatrix.tsx`) sets own / team / department / everyone per enforced key, writing `permission_scopes` rows with `subject = 'role'`. "Everyone" is the *absence* of a rule, so choosing it deletes the row and returns the key to the system default. Keep `SCOPED_KEYS` in step with `scope_enforced_permissions()`.

## Scope for files, the wiki and chat (schema 0049)
- **`file_in_scope` / `wiki_in_scope` / `channel_in_scope`** complete the set. Files and the wiki are enforced in their **RLS policies** (`files_read`, `wiki_read`); chat is enforced inside **`can_view_channel`**, which every chat read already funnels through. Same contract throughout — narrows only, inert with no rule. Enforced keys are now `people.edit`, `tasks.view`, `projects.view`, `files.view`, `wiki.view`, `chat.view`.
- **`search_all` had to be changed too, and this is the general lesson.** It is SECURITY DEFINER, so RLS does not apply to it and each branch re-implements its own checks. Wiring the policies alone left global search able to surface a narrowed file's name and folder. **Whenever you narrow a table, check whether `search_all` reads it directly** — `test_access_control()` now asserts search keeps calling `file_in_scope` and `wiki_in_scope` so this specific leak cannot come back, but a new table needs its own assertion.
- **Membership is the floor for chat, above even "own".** A person in a channel keeps it whatever the rule says, and a DM is never scoped away from its participants. Files fall back department → project's department → owner's department; wiki falls back to its author's; nothing unfiled can escape a department-scoped reviewer.
- **Both new SELECT policies carry a direct owner branch** (`owner_id = auth.uid() or file_in_scope(id)`, `author_id = auth.uid() or wiki_in_scope(id)`) — not decoration. `test_returning_policies` caught `files_read` the moment the predicate went in: a STABLE helper reading the table it guards runs against a pre-write snapshot, so `.insert().select()` would read back nothing. The helper already returns true for the owner, but only the policy text is visible to the planner. See `docs/TESTING.md`.
- Verified 0 drift across every active person (5 files / 15 wiki / all channels unchanged), narrowing confirmed to bite (wiki 3→0→3, channels 12→11→12), and the search leak confirmed closed and then reopened by removing the rule. `platform_self_test()`: 19 passed, 0 failed.

## Tenant isolation for the authority tables (schema 0050)

- **`user_roles` and `permission_overrides` carried no `org_id`**, so neither could have a policy mentioning `current_org()`. Their predicates were row-independent — `is_admin() or is_hr() or has_admin_perm('security.manage')` says nothing about *which* row is being touched — so once a branch was true it was true for **every row in the table, in every company**.
- **Demonstrated before it was fixed**, against a company-B person created inside a rolled-back transaction: a company-A director read their role grant, read their individual override, and **deleted the override**. The override was a *deny*, so deleting it grants that person access in a company the actor has nothing to do with. Re-run after the fix: 0 rows read, 0 deleted, and the escalating insert refused with *“That person is not in this company.”*
- **The guards did not close it**, and the reason generalises: `guard_permission_override` did check the target's company but is `BEFORE INSERT OR UPDATE`, so **DELETE never reached it**; `guard_user_role` had no company check at all. A trigger that skips an operation is why the tenant boundary belongs in RLS, on a column — a policy cannot skip a command.
- **`has_perm` joined `user_roles` to `system_roles` with no company test**, so a role belonging to company A attached to a person in company B would have granted its permissions inside company B. Now `sr.org_id = p.org_id` in both the deny and the allow tier. Verified 0 such rows exist, so it changed no live answer — it removed the possibility. Verified 630 user × key combinations against the pre-0050 logic recomputed inline: **0 drift**.
- **The company on an authority row is derived, never supplied.** `authority_row_org_default()` reads it from the *subject's* profile and overrides whatever the caller passed, so nobody can file a grant under the wrong company. The column also has `default current_org()` — not for correctness but because `NOT NULL` with no default makes the generated TypeScript `Insert` type demand the column at five call sites that have no business knowing it.
- **Why the self test had been reporting this as fine.** `tenant:no_org_column:review` read `rep->'child_tables_no_org'` and coalesced a missing key to `[]`. `tenant_isolation_report()` never emits that key, so the line printed “every non-global table carries org_id” on every run while 65 tables did not. **Coalescing an absent key to empty turns “not measured” into “nothing to report”** — the report now computes the list itself. It correctly reports 61 tables today (most legitimately reach their tenant through a parent).
- **`authority_tables()` is the list that may not rely on a parent**: `user_roles`, `permission_overrides`, `permission_scopes`, `system_roles`, `role_defaults`, `permission_changes`, `system_role_versions`. `access:authority_tables_tenanted` fails if any of them lacks `org_id` or an org-scoped policy, and `access:no_cross_company_roles` fails if anybody holds a role from another company. The review line cannot catch this class because it is informational by design — authority needs a check that is allowed to fail.

## Safe admin delegation — the roles.* keys become real (§15, schema 0051)

- **Four keys had been gating nothing.** `roles.create`, `roles.edit`, `roles.delete` and `roles.assign` have been in the catalogue since 0040; role administration was actually reached through `is_admin()`, which is `role_rank(current_role_level()) <= 2`. Three directors could edit and assign security roles for no reason but their rank — the exact thing §3A committed against. **A key that appears in the matrix, can be granted and revoked, and changes nothing is worse than no key**, because somebody will grant it and believe they delegated something.
- **Seeded before enforced, because making a key real is a narrowing.** The seed is small: all four `roles.*` keys and both `access_control.*` keys already alias `security.manage`, so every security administrator resolved them anyway. Only the level route needed writing down — `director` and `executive` level defaults, which is exactly what `is_admin()` covered. `super_admin` needs nothing (has_perm has an unconditional branch); the two roles holding `people.manage`/`hr.manage` are both Company Super Admin, which holds `security.manage`.
- **`admin_roles` was deliberately NOT seeded.** “HR Admin” lists `people.manage`, and letting that keep implying role administration is the over-grant §15 exists to remove. It has no holders, so nobody is affected — but this is the one place the change is intentionally not behaviour-preserving, and that is the point of the section.
- **Split per command**, because §15 names them separately and one `FOR ALL` policy cannot tell “may create a role” from “may delete one”: `sr_insert`/`sr_update`/`sr_delete` and `ur_insert`/`ur_update`/`ur_delete`. `has_admin_perm` not `has_perm`, so the `admin_assignments` wildcard route keeps working. **The manager branch on `user_roles` is untouched** — a manager assigning a role no stronger than their own level to their own report is a real workflow §15 does not ask anyone to remove.
- **Verified end to end, with row counts not exceptions.** `UPDATE`/`DELETE` filtered out by RLS affect zero rows *silently*; only `INSERT … WITH CHECK` raises. A first probe that measured “no error” reported everything working when it was not measuring anything — **never test an RLS write by catching an exception.** With row counts: all five active people keep create/edit/delete/assign, and denying `roles.edit` on one director stops role editing (t→f) while create and assign stay intact.
- **New `delegation` suite**, asserting the reverse direction from the scope checks: every key that *names* a capability must be referenced by some policy (`delegation:keys_enforced`); no policy on the authority tables may grant on `is_admin()` (`delegation:authority_not_from_rank`); and create/edit/delete must be separately gated (`delegation:role_commands_separate`). The second check **failed on its first run** and found `po_read` still granting by rank — fixed to `access_control.view`.
- **UI**: `AccessCaps` is passed from the page into `AccessStudio` → `RolesTab` / `RoleMatrix` / `PersonAccess`. New, Duplicate, the tri-state cells, Review change and Change are each disabled with a tooltip naming the missing key, and a read-only viewer gets one line explaining that reading this screen and changing it are different permissions. **The flags are a courtesy, never the control** — every write still goes through RLS.

## Authority changes are announced (§20, schema 0052)

- **Nothing told anybody.** `user_roles` and `permission_overrides` carried guard, history and org triggers and notified no one — a person could be given, or quietly stripped of, a security role and never hear about it. The only table in this area that notified anything was `admin_assignments`, the legacy path, which has no holders at all.
- **Two audiences.** The **subject**, always — it is their access, and §33's principle is that everything an employee's data shows is visible to the employee too. The company's **other super admins**, for *sensitive* changes only. “Sensitive” is not a judgement call: it is whether the catalogue marks the key `risk = 'high'`. The actor is never notified of their own action and the subject is never told twice.
- **Events**: role assigned / removed / expiry changed (`notify_role_grant`), individual allow / deny / rule removed (`notify_override_change`), account deactivated or reactivated and Super Admin level gained or lost (`notify_account_change`). All `kind = 'security'`, so they fan out to web push through the existing `notification_push_fanout()` — inserting the row is the whole delivery mechanism.
- **Department change is deliberately NOT covered.** `apply_transfer` already notifies the subject, and a trigger cannot tell whether that RPC is driving the update, so a trigger here would double-notify the sanctioned path. **A department change made outside the transfer flow (bulk import, direct edit) still notifies nobody** — a known gap, recorded rather than papered over.
- **The profiles trigger carries a `WHEN` clause** (`old.is_active is distinct from new.is_active or old.role is distinct from new.role`), so ordinary profile edits never enter the function at all.
- `delegation:authority_changes_notify` asserts the three triggers are attached, because a detached notification trigger looks exactly like a system where nothing is happening.
- **Fixed in passing**: `KIND_ICON` in `NotificationsPanel.tsx` had no entry for `security` or `help_request`, both valid `notification_kind` values, so those notifications rendered with an empty icon slot. Every notification this migration adds is `security`.

## Bulk administration (§29)
- `BulkActions` in `src/components/admin/people/BulkImport.tsx` (reached from **Admin → HR → Employee records → Bulk import**) does five things to a multi-selection: **give a role, take a role, change department, change manager, deactivate**. Give/department/manager already existed; take and deactivate close the asymmetry where authority could be handed to fifty people in one action and had to be taken back one at a time.
- **Destructive actions take a typed CONFIRM**, not just a second click on a familiar dialog — `DESTRUCTIVE` lists them, the apply button is disabled until the word is typed, and it turns danger-toned. Everything still goes through the same preview.
- **You are always excluded from role and deactivate actions on yourself.** The database refuses a self-grant, a self-revoke of the last admin role and self-lockout anyway, and one refusal would fail an entire batch with a message about the wrong thing — so the selection filters you out and says so. This is a real trap because "select visible" includes the person clicking.
- **Revoke and deactivate iterate per person**, deliberately, rather than issuing one statement: the last-Super-Admin guard refuses the final holder, and a single statement would fail the whole batch without naming who caused it. Errors are reported as `Name: message`.
- **The revoke preview asks the honest question** — of the people ticked, who actually holds this role — because revoking from somebody who never had it is a no-op and would otherwise overstate the count in the confirmation. It also warns that removing a role does not necessarily remove the access: the same permission may still arrive from a department, a level or another role. Use "Why?" in Access Control for certainty.
- Deactivation reuses `change_impact(p_user)` as its preview, which is exactly the right question — reports left without a manager, approvals left unanswered, responsibilities left unowned.

## Role templates and creating a company's own roles (schema 0048)
- **Before this, no role could be created at all.** The Roles tab listed and edited the seeded roles and offered nothing else, so "a company defines its own roles" was untrue — and it could not have worked anyway, because creating a role raised until the `log_permission_change` bug was fixed in 0041.
- **`role_templates`** is a global, platform-curated catalogue of starting points (same shape and RLS posture as `company_templates`): HR Administrator, Department Manager, Finance Manager, IT Administrator, Auditor, Content Writer, Content Publisher, Designer, Developer, Sales Employee, Customer Support, Read Only. Their permission lists use the granular `module.action` keys from 0040 throughout — that is what those keys are for.
- **A template is copied, never linked.** The company owns the result from the moment it is created and editing it later has nothing to do with the template. Nothing in `system_roles` references `role_templates`; a starting point that keeps editing itself is not a starting point.
- **Authority is not the template's problem.** `guard_system_role` already refuses, by name, any permission the creator does not hold — so a template richer than the creator's own authority fails loudly naming the key, rather than quietly producing a weaker role. The modal shows that message verbatim instead of pre-filtering the list, because it tells the creator exactly what they are missing. Verified: a company admin creating from a template succeeds; the same admin inserting a `platform.*` key is refused with *"You are not allowed to put … in a role."*
- **Duplicate** copies an existing role's grants *and* its denies into a new one, leaving the original untouched.
- **Two guards on the templates themselves**: `guard_role_template` refuses a template naming a key that is not in the catalogue, and `test_access_control()` re-checks the same invariant every run — the trigger cannot catch a key that leaves the catalogue after the template was written.
- **UI**: `NewRoleModal` in `src/components/access/NewRoleModal.tsx`, opened from **New** on the Roles list or **Duplicate this role** above the matrix.

## People directory: job title, access level and security roles side by side (§12, §3A)
- `useSecurityRoles()` (`src/components/people/useSecurityRoles.ts`) returns a `Map<userId, SecurityRole[]>` for the screens that list people, and `<AccessRoles/>` in `PeopleBits.tsx` renders them under an explicit **Access** label. Used by `/people` (the directory cards) and by **Access Control → People**.
- **The three facts stay separate on screen**, which is the whole point: the **job title** (`designation`) under the name says what someone does, the **access level** (`profiles.role`) beside the department says where they sit, and the **security roles** are the only one of the three that grants anything. Labelling the last "Access" is what stops "Senior Content Writer" reading as authority.
- **Expired grants are filtered out in the hook** — an expired role is not authority any more and must not read as any.
- **"No roles shown" means "none *visible to you*", never "none held".** `ur_read` gives a person their own roles and gives managers, HR and security administrators everyone's, so an ordinary employee gets a map containing only themselves (verified: admin and manager see all grants, an employee sees zero). Every consumer renders nothing in that case rather than printing "None", which would state something the viewer cannot actually know.
- The embed accepts PostgREST returning `system_roles` as an object *or* a single-element array, since which one you get depends on how the relationship is inferred.
